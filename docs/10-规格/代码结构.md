## 这份文件的地位

它规定代码怎么分、谁许 import 谁。

**改结构以前先改这份文件**，然后改 `tests/contract/import_rules.py` —— 它是这份文件里唯一被机器强制的部分。

检查逻辑只用标准库，**没装 pytest 也能跑**：

```powershell
python tests/contract/import_rules.py
```

pytest 版本 `tests/contract/test_import_rules.py` 只是它的外壳。

配套阅读：[总体架构与技术栈.md](../90-归档/总体架构与技术栈.md)（已归档，9 部分划分的原始论证）、[DSH平台事实.md](../30-专题/DSH平台事实.md)、[安装与分发.md](../40-讨论稿/安装与分发.md)。

## 四条解耦规则

**规则一：依赖只朝一个方向。** `contracts` ← `engine`、`contracts` ← `offline`，两边都 ← `runtime`。**`engine` 永远不 import `offline`。**

**规则二：设备层是端口，不是实现。** `engine/device/` 只放适配器，端口定义在 `contracts` 里。所以"离线重放"不是特例代码，只是换一个适配器 —— 这是"视觉层必须能被离线驱动"那条地基约束的落地方式。

**规则三：引擎对外只认自己的语义。** `engine/api/` 是算子清单，`engine/mcp/` 只做翻译。`engine/` 里除 `mcp/` 之外不许出现 MCP 字样，换桥接不用动引擎。

**规则四：契约层只有数据和接口，不 import 任何内部模块。** 它是唯一被所有人 import 的东西。

### 一条更细的规则

**`engine` 的六个子包互不 import。** 数据流向是 `device → vision → state → timeline → control → api → mcp`，但那是**数据流向，不是 import 关系**：每一环之间靠 `contracts` 里的端口连，具体实现在 `runtime/wiring.py` 注入。

唯一的例外是 `mcp/` 依赖 `api/`，因为桥接层需要算子清单。

**如果这条约束将来证明太紧，正确的做法是改规则并记一条决策，不是偷偷加 import。**

## 边界与收益

| 边界 | 拦住了什么 | 怎么强制 |
| --- | --- | --- |
| `contracts` 不 import 内部 | 契约被实现污染 → 所有人都依赖所有人 | 导入规则测试 |
| `engine` 不 import `offline` | 线上混进生成器与重放逻辑 | 导入规则测试 |
| `engine` 子包互不 import | 改一处动全身 | 导入规则测试 |
| 只有 `engine/mcp/` 带 MCP 字样 | 引擎被某个桥接绑死 | 导入规则测试 |
| `assets/` 与 `data/` 分开 | 生成物和运行时垃圾混在一起，gitignore 没法写 | 目录本身 |
| `vision/` 不解释语义 | 视觉层越界，改一处崩多处 | **只能靠 review** |

**能被机器拦住的只有 import 关系。** 命名、词汇、职责有没有越界，仍然靠人。

## 尚未落地

- **叶子模块等写到的时候再建**，见 [决策记录 D-全局-03](../20-决策记录/全局.md)。**包内的切法跟着 `10-规格/` 的节走**：`contracts/` 已按[契约层](契约层/README.md) 的五节开出 `slot.py` / `geometry.py` / `scale.py` / `containers.py` / `ports.py`——**这一层的叶子齐了**（**不预建空文件**）。
- **入口点。** `pyproject.toml` 里的 `[project.scripts]` 是注释状态，因为叶子模块还不存在，指过去会指向不存在的模块。
- **`tests/offline/` 还没建**，有测试了再建，不预建空目录。`tests/spec/` 与 `tests/unit/` 的分工见 [D-全局-17](../20-决策记录/全局.md)。
- **端口完备性测试**（**T4 落地**）：`contracts` 里定义的每个端口，在**装配那一刻**都有一个实现者。端口已经有了（[契约层](契约层/README.md) §5 四个），而判据落在这里——资产与样本的"适配器"按设计就是**空实现**（[端口与错误](契约层/端口与错误.md)），所以"有没有实现"只有在 `runtime/wiring.py` 把它们接起来时才答得出来。落在 `tests/contract/port_completeness.py`，与 `import_rules.py` 同类（标准库、不装 pytest 也能跑）。
  **判据是方法级的，不是对象级的**（T4 撞到）：一个适配器可以在、而它的某个方法**故意没接**（设备端口就是这样），所以"可用适配器"这个词撑不住——真正可判的是**方法在不在** + 下面那条登记。
- **欠账登记：`runtime/wiring.py` 的 `PORT_GAPS`。** 一个端口方法**这一轮故意不接**时，必须在这里留一条（哪个端口 · 缺什么 · 归哪一轮）。**"还没接"必须是写下来的，不许是"忘了"。** 它与上面那条是一对：测试问"接上了吗"，登记答"没接的是哪几条、为什么"。
  **"留空" = 方法不存在**，不是"方法在、抛 `NotImplementedError`"：一个在但一调就炸的方法，会让"接上了"这个判断变成假的。
