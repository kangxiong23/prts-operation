# 设备层

> 状态：讨论中 ｜ 三层与部署路径已走通、时钟校准与取像已写；**朝向取法与 `r` 等真机项已列出**

对应代码：`src/ark/engine/device/`。

## 这份文件负责什么

**把"一个游戏动作"变成"手指落在正确的地方"，再从屏幕上取回一帧。** 整个项目里唯一接触真机的地方。

它是「端口 + 适配器」结构：端口定义在[契约层](契约层/README.md) §5，这里只放适配器。

| 适配器 | 用途 | 什么时候做 |
| --- | --- | --- |
| `adb/` | 真机：`screencap` 取像、`input` 注入 | 第一个做 |
| `replay/` | 离线重放：读录制的帧、只记动作不真的点 | 随[采集与验收/离线验收.md](采集与验收/离线验收.md) 一起来 |

**它的正确性判据只有一条**：给一个动作，我把手指放对地方。**它不知道动作有没有生效**——那是视觉层与生效反馈的事（[接口层/执行与失败](接口层/执行与失败.md) §3）。这条边界不能糊。

## 1 三层，共用一条词汇表

```
adb 基础操作        screencap ｜ input tap ｜ input swipe ｜ input keyevent ｜ wm size
      ↓ 封装
手势原语            按 ｜ 拖 ｜ 抬 ｜ 点 ｜ 键            ← 对设备负责：手指真的动了
      ↓ 组合
游戏动作            部署 ｜ 撤退 ｜ 开技能 ｜ 关技能        ← 对游戏负责：点对了地方
      ↓
轴的动词            [时序层](时序层.md) §4                ← 一模一样，不翻译
```

- **对外面就是轴的动词表**：轴上有什么动词，这里就有什么入口。[接口层](接口层/README.md) §2② 那条"不存在第二套词汇"因此从 AI 一路贯通到手指；
- **这里的叫「手势原语」**：「原语」那个名字留给**视觉原语**（[视觉层/原语.md](视觉层/原语.md)），别混（[时序层](时序层.md) §4）；
- **动作面之外只剩"设备管理"**：连接状态、分辨率与方向、取一帧。它们**不是动作**，不占动词表。

**手势原语的参数是格坐标与朝向，不是像素。** 像素在这个入口内部由 `格坐标 ↔ 像素` 投影算出。两条理由：

- **慢放是另一套投影**（地图右移倾斜，[控制层](控制层/时间态.md)）——让每个调用方自己换算，等于把"慢放下必须换一套"这条纪律复制到每个调用点；
- 调用方本来只有格坐标，没有理由让它碰像素。

## 2 部署（样板）

| 级 | 长什么样 |
| --- | --- |
| 轴 / 算子 | `部署(能天使, (5,4), 右)` |
| 游戏动作 | 按住备战席那张卡 → 拖到目标格 → 选朝向 → 松手 |
| 手势原语 | **一次拖动**：`拖到(格心 + 朝向向量 × r)`——按下与抬起是它的两端 |
| adb | 一次 `input swipe x0 y0 x1 y1 <duration>`：起点 = 那张卡，终点 = 上一步那个点 |

**两件事让它塌成一次直线 swipe**：

1. **朝向取的是"手指相对格心"的方向** → 同一个终点 `格心 + r·û` **同时编码了格与朝向**；
2. **`input swipe` 是原子的**——手指**无法跨越两条 adb 命令保持按下**。所以部署**必须是一次性手势**，不能"先拖到格、停一下看清预览、再选方向"。代价可以接受：**设备层本来就不该在途中做判断**。

**朝向是必填**（[时序层](时序层.md) §4）：不选朝向 = 一次未完成的放置。所以这个终点**永远带朝向**，没有"只给格"的形态。

**`r` 被两边夹住**，这是这条路唯一的未知数：

| | 约束 | 违反的后果 |
| --- | --- | --- |
| **上界** | 终点必须落在**可部署区域**内 | 松手位置不可部署 → **整次部署被撤销**（用户确认） |
| **下界** | **4 个朝向**（上下左右，**不含斜向**）要分得开 | 朝向定不下来 |

估 `r ≈ 0.3 格`，**格越小越紧**，实测。

**4 个朝向让下界松了不少**：四个终点都落在**本格之内**（`r ≈ 0.3 < 0.5`），所以上界（终点落在可部署区域内）也更容易满足。**曾写作"8 个朝向"——已改**（用户确认不含斜向）。

**拖动途中离开有效区域不会取消**（用户确认）——取消只看**松手位置**。

### 一条只能真机回答的风险（未验）

上面第 1 条假定游戏取的是**"松手位置相对格心"**。若它取的是**"最后一段拖动方向"**，那么从卡片直拉到 `格心 + r·û` 时，末段方向是"卡片 → 终点"的方向，**不等于 `û`，朝向会错**。

修法是让路径末段沿 `û`——而 `input swipe` **只能画直线**，那就必须换 **`input motionevent`**（DOWN / MOVE / UP 分三条命令，**它的可用性也要验**）。

> **这条不只是个数值问题**：它决定**设备层要不要支持多命令手势**。真机一验就知道。

### 另外三个动作

`撤退` / `开技能` / `关技能` 是同一个形状：**点已上场干员 → （面板出现）→ 点面板上的按钮**。

- 两条命令 + 一个**等待面板出现**；
- 那个等待**不是判断**（等的是一件确定会发生的事），但**也不能盲等**——见 §5 的"节奏"；
- **它们都不能在暂停态做**（暂停态选不中已上场的干员，[控制层](控制层/时间态.md)）→ 都由 `继续到` 在跑到那一帧时注入。

## 3 时钟校准

**要校准的不是"时钟"，是"注入落在哪一刻"。** 逻辑帧**不从墙钟直接来**（[时间基](../30-专题/时间基.md) §4：秒表为主轴、费用相位校准），所以这里**只产出墙钟耗时**；折成帧是控制层的事——[契约层](契约层/README.md) §3 已经把这两种刻度在类型上分开了。

三样，产出**区间**而不是一个数：

| 量 | 怎么测 | 用在哪 |
| --- | --- | --- |
| **取像往返** | `screencap` 发起到拿到完整帧；**背靠背连抓两帧，用费用条量**（`Δ整数 + Δ相位`，±7 ms——比秒表准，见 [时间基](../30-专题/时间基.md) §3.2） | 判定节拍的预算（[控制层](控制层/识别时机.md) §7 那条"跟不上要上报"） |
| **注入往返** | `input` 发起到命令返回 | "这个动作落在哪一逻辑帧"的误差 |
| **手势耗时** | `swipe` 的 `duration` 参数 vs 实际墙钟 | 部署的稳定性预算 |

**取像往返已实测**：**0.9 s**（原始 RGBA）／1.2–2.2 s（PNG，随画面复杂度浮动）。见 §4。

**而"往返"要拆成三段**：`发命令` → `设备端 screencap 返回` → `pull 返回`。**帧内容的时刻在中间那一段里**——[首轮探索/时间对齐](首轮探索/时间对齐.md) §3 记的假设是"**画面内容对应发起时刻**（延迟主要在传输）"，**这条假设要实测**：若帧时刻其实落在设备端段的另一端，用整个往返去减就会**恒偏**，而 `round` 的容差只有 **±0.5 费**（[时间基](../30-专题/时间基.md) §3.3）。

**而且它只需要钉一次**：所有帧共享同一个 `−a·Δ` 偏移常数，钉住一次之后，运行中每一帧的时刻由**差值**给出，系统性偏差自动抵消（[时间基](../30-专题/时间基.md) §4）。**要的是抖动幅度，不是每次重测。**

**还有一条更简单的实测法，它不用拆段**：**借首轮探索的录像**。原始静帧按**内容**匹配到录像里的某一帧（录像 30–60 FPS，最近那一帧就在 1/60 s 内），而那一帧的时刻由**它自己的相位**给出——于是

```
Δ_true = t_recv − 那一帧的时刻
```

**直接量出来**，一段都不用拆。见[首轮探索/README](首轮探索/README.md) §2。

**一个容易搞反的点**：**墙钟延迟本身不随慢放改变**——慢放改变的是"同一条墙钟折成多少游戏帧"（[契约层](契约层/README.md) §3：200 ms 在常速是 6 帧、慢放是 0.6 帧）。所以**校准的产物存成墙钟**，折算留给控制层。

**慢放倍率借这里的手测**（预期 10 倍，未实测）：用费用读数测（[时间基](../30-专题/时间基.md) §4），而**测量动作本身走的就是这一层的取像与注入**。设备层出**工具**，倍率值归时间基。

**部署的慢放不建模**（用户确认）：按下卡片即进慢放、松手即退，而 adb 一次注入**不跨帧**——所以部署本身没有"慢放窗口"可供利用。**慢放的两条来源里，只有"点开详情面板"那条是给 AI 读值用的。**

## 4 取像

- **通道先用纯 adb**，不装 `scrcpy`（[D-全局-05](../20-决策记录/全局.md)）；**而首轮探索另走 `screenrecord`**（[D-全局-20](../20-决策记录/全局.md)），它的实测参数见 §6；
- **格式走原始 RGBA，不走 PNG**（[D-全局-19](../20-决策记录/全局.md)）：`screencap` **不带 `-p`**，取回**走设备端写文件 + `adb pull`**。`exec-out` 直出**不更快**（PNG 1.3 s、原始 1.9 s——原始反而更慢，14 MB 走流式通道比 `pull` 慢）；**PowerShell 的 `>` 会毁掉二进制**，别用它取原始。实测 0.9 s 定长 vs PNG 1.2–2.2 s 浮动；两种格式**颜色编码一致**，所以颜色阈值不用重标；
- **原始帧的字节布局（这就是"帧"的定义）**：头 **16 字节 = 4 个小端 uint32**（宽 · 高 · 像素格式 · 色彩空间，实测 `2800 1260 1 1`），后接 **宽×高×4 字节，通道序 RGBA**。通道序是验过的：生命值那片 R 占优的粉，按 RGBA 解出来 R≈254 远大于 G/B，按 BGRA 解就反了。所以一帧定长 **14,112,016 字节**。视觉层的入口照这个解。**只认「像素格式 = 1 且色彩空间 = 1」这一种**——别的值**报错拒绝**，不许按 RGBA 猜着解（那就是假事实）；将来设备报出别的值，这一条再开；
- **取像往返约 0.9 s，所以"抓帧很快"这个假设不成立**：抓帧期间画面还在跑，**常速 ≈ 27 逻辑帧、慢放 10× 下 ≈ 2.7 帧**。所以"**判定发生在慢放态**"从优化变成**前提**；
- **延迟补得回来——帧自己带着时间戳**：费用严格 1 费用/秒，**费用条相位**给出这一秒之内的小数（轨道 **153 px**、一个费用点 30 逻辑帧 → **约 0.196 帧**）。**读这一帧的费用条相位，就知道它是哪一逻辑帧**，所以"±0 帧"靠读帧自己的相位兑现，不靠"抓帧快"。相位是什么见 [状态层/全局与HUD](状态层/全局与HUD.md)「当前费用」，几何见[视觉层/顶部HUD与数字](视觉层/顶部HUD与数字.md)；
- **取像端口返回原始帧，不返回归一化帧**（用户裁定）：这一层只管"帧到手"，不该知道画布；归一化是[视觉层](视觉层/README.md) 的入口，画布的定义在[契约层](契约层/README.md) §2；
- **只有"取一帧"，没有"取像流"**：一次识别现抓一帧，**没有常驻取像**（[控制层](控制层/识别时机.md)）。所以这一层不需要缓冲、不需要后台采集；
- **"抓帧在按暂停之前"是调用方的顺序**（[控制层](控制层/识别时机.md)），不是这一层的职责；这一层保证的是"帧到手"，**而"多快"是个已知的 0.9 s**（见上），不是可以假设的东西；
- **分辨率与方向**查出来喂**前提头**校验（[时序层](时序层.md) §3）：不吻合则所有 ROI 与投影一起失效，**报错拒绝执行，不降级**。
  - **而 `wm size` 与画布差 90°（实测）**：这台机器 `wm size` 报 `Physical size: 1260x2800`（**竖屏自然朝向**），画布却是 **2800×1260**（横屏）。**两个口径不许混**：写 `wm size` 参数时按**它自己的口径**（想要 2800×1260 就写 `1260x2800`），比对前提头时按**画布口径**（2800×1260）。**搞反了游戏可能进信箱模式，而"比例守恒"那条用户裁定会跟着失效。**

## 5 端口、节奏与重放

**端口必须"纯"到 replay 适配器能满足**（[契约层](契约层/README.md) §5）——"离线重放不是特例代码"的落地条件就是换一个适配器：

| 端口方法（名字在[契约层](契约层/README.md) §5） | `adb` 适配器 | `replay` 适配器 |
| --- | --- | --- |
| `grab_frame` 取一帧 | 真抓 | 返回该帧号对应的录制帧 |
| `inject_gesture(at, facing)` 注入手势 | 真点 | **只记一笔，不点** |
| `device_facts` 设备事实（分辨率 / 方向） | 查真机 | 从录制的前提头里回放 |

**三个方法的名字与签名是接口的一部分**——下一个适配器与所有调用方都要照着写，所以列在这儿；**类型**定义在[契约层](契约层/README.md) §5。

**`facing` 是字符串**（四个朝向：上下左右，**不含斜向**；词表在[时序层](时序层.md) §4）——**契约层不为它开类型**，理由是**读回来那一侧也是字符串**（[契约层](契约层/README.md) §1 的「精确」值域里，`heading` 就是字符串载荷）：同一套词汇在"送出去"和"读回来"两侧必须同型。

**设备事实的返回形状是具名冻结数据类** `DeviceFacts(resolution: Canvas, orientation: str)`——与 §2 宁可要 `GridCoord` / `Pixel` 两个类型也不用裸元组是同一条规矩。`orientation` 的取值词表**不在这两层**：它是设备报出来的环境前提，与 `end_reason` 同理（[契约层](契约层/README.md) §5）。

**"节奏"是这一层的内部事，而且它不是判断力**：面板要等它滑出来、点击要等上一次手势的基础间隔过去。判据是"**确定会发生的等待**"，**不是"看情况决定"**——后者违反[接口层](接口层/README.md) §2① 的粒度线。**等多久、要不要重试属于落地的事**，[控制层](控制层/识别时机.md) 已注明推迟。

**墙钟超时属于这一层**：命令没返回要报**中止**（[契约层](契约层/README.md) §5 的第三种错误），而不是无限等。

## 6 前置与真机实测清单

**前置**（开工前）：装 `adb`（platform-tools，[D-全局-05](../20-决策记录/全局.md)）· 唤醒屏幕 · 保持常亮 · 关掉会抢触摸的系统手势。

**`screenrecord` 已实测**（vivo V2338A · 安卓 16 / SDK 36 · v1.4）：可用、录到真游戏画面、原生分辨率、均值 59.9 FPS、**长 GOP**。**参数表住在它的使用方**——[首轮探索/README](首轮探索/README.md) §2.1。

| 待实测 | 卡住什么 |
| --- | --- |
| **朝向取法**（松手位置 vs 末段方向） | **要不要支持多命令手势** |
| `r` 的取值 | 部署能否一次成功 |
| **落地几帧才能选中** | 同一干员的动作最小间隔（[时序层](时序层.md) §4） |
| **注入 / 手势**两个墙钟耗时（**取像已实测 0.9 s**） | [控制层](控制层/识别时机.md) §7 的"跟不上"判据 |
| 慢放倍率 | [时间基](../30-专题/时间基.md) |
| `input motionevent` 在目标安卓版本上是否可用 | 同第 1 行 |
| 面板出现要等多久 | §5 的节奏 |
| **「启动」后战斗界面多久出现** | [`启动`](接口层/算子清单.md) 的生效反馈——它就是"确定会发生的等待"，属这一层的节奏 |
| **取像往返拆三段**（发命令 / `screencap` 返回 / `pull` 返回），以及**帧时刻落在中间那一段的哪一端** | §3 的 `Δ` 能不能用整个往返去减——`round` 的容差只有 ±0.5 费 |
| **暂停灰罩的 α**（整屏变灰是不是一个均匀标量） | [控制层](控制层/识别时机.md) §4 的"决策帧在暂停后抓"能不能成立 |

## 尚未定

- **多点手势要不要支持**——取决于"朝向取法"那条；
- **要不要用 `wm size` 把取像分辨率降下来**：这是最大的提速杠杆（原始帧字节数按面积缩），而且**比例守恒**（用户裁定）——**同一套 UI 在两边的相对位置一致，旧测量按比例就能换算过去**（已验两处，见[视觉层/顶部HUD与数字](视觉层/顶部HUD与数字.md)「坐标口径」）。所以它**不像原先写的那样要"全部重测"**。要认的代价只有两条：**数字变小**（费用数字现在高 59 px，降到 1400×630 只剩约 30 px，识别裕度掉一半），以及**比例守恒在"固定像素尺寸的元素"上会破**（描边、字号）——所以降档之后要在真帧上抽验几个硬边。**必须在首轮探索之前定**——投影标定是最贵的一次人工校准。定的时候先量一张"各档分辨率各多少帧率、数字还剩多少像素"的表；
- **`screenrecord` 的参数与可用性**（**通道已定**：首轮探索走它，[D-全局-20](../20-决策记录/全局.md)）：`--time-limit` 要不要分段 · 目标分辨率与码率 · **编码器丢帧多少** · 录制文件体量与拉回耗时 · **这台安卓版本上 `screenrecord` 是否还在**（新版安卓有移除的先例）。它输出 h264、可以用已在栈里的 opencv 解，帧率能到几十。
