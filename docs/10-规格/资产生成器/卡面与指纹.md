# 卡面与指纹

> 状态：讨论中 ｜ 已立；**两侧同款、同尺度已实测**（见[视觉层/备战席点名](../视觉层/备战席点名.md)）；编队页**原生帧已到手、坐标已量**

落到 `assets/roster/`，**进版本库**（见 [README](README.md)、[D-全局-10](../../20-决策记录/全局.md)）。它是**五样产物之一**。

## 0 两样东西，一个目录，两个键

| | **卡面** | **练度指纹** |
| --- | --- | --- |
| 记什么 | 这个账号上这个干员**长什么样** | 他**练到什么程度** |
| 键 | **干员 × 精英化 × 皮肤** | 卡面那个键 **+ 等级 × 技能等级 × 模组 × 潜能** |
| 谁用 | 认备战席的卡片是谁（[特征库](特征库.md) §1） | 算基础值（[基础数值](../状态层/基础数值.md)）· 轴的复现性（[时序层](../时序层.md) §3） |

**两个键不一样，这点要说清**：等级、技能等级、模组、潜能**不改变卡面**——只有**精英化与皮肤**改。所以升一级，卡面照旧，指纹却要新的一条。

**而皮肤只改卡面、不改数值，却仍然进指纹的键**——因为轴的复现性也依赖"这个干员长什么样"（用户裁定：精英化与皮肤都进练度指纹）。

**为什么同一个目录**：它们是**同一趟采集**的产物（§1），而且卡面是"这一条指纹属于谁"的凭据。

### 卡面是卡片上的哪一块：不是整张卡

**身份识别区只取立绘那一块**（用户裁定）—— 整张卡上还有两样东西，**都不能进身份区**：

| 卡上的东西 | 为什么不能进身份区 |
| --- | --- |
| **职业图标** | 它**不唯一**：8 个职业对着 418 个干员（[游戏数据库](游戏数据库.md)），一个图标对应几十个人 |
| **需要消耗的部署费用** | 它**会变**：死亡或被撤退 `n` 次后 = 初始费用 × (1 + n/2)（[游戏数据库](游戏数据库.md) §已收集）—— 同一个干员的同一个卡面，**在不同时刻长得不一样**，指纹就不稳 |

**而"立绘里的哪一小块"还有一条实测结论**：取**脸上那一块**，不取整块立绘 —— 见[视觉层/备战席点名](../视觉层/备战席点名.md) §判据的形状。

**而这两样都别丢，只是不跟立绘挤在同一个矩形里**：费用数字是**要单独读的字段**（[游戏数据库](游戏数据库.md) 明说"直接读比算更可靠"）；职业图标**倾向**当**候选集约束**用（先缩到本职业那几十个，再比立绘）—— 但这只是倾向，**还没裁定**。

## 1 从哪来：`启动` 顺手截图 + 人点名（兼注册）

**采集不单独占一个动作**——它挂在算子 [`启动`](../接口层/算子清单.md) 上（用户裁定）：

```
人把词条选好、队伍配好，停在编队页
  → AI 调 `启动`
      ├─ 顺手截一帧编队页
      ├─ 按固定位置裁出每张卡（位置固定 → 规则匹配，不用找）
      └─ 点「开始行动」
  → 卡面落盘
  → 进战斗后的第一眼：人点名（第几张卡是谁），顺手补注册没见过的新组合
  → 进 assets/roster/
```

**名字怎么来 —— 已改：读出来，不再靠人注册**（用户裁定）：卡片下缘确实印着名字（**白字压在一条深色横带上**，右对齐到卡左缘 + 208），而且**印的是皮肤名**（"凛御银灰"是银灰的皮肤、"圣聆初雪"是初雪的皮肤）—— 所以名字与立绘是同一件事（D-全局-36）。做法是**裁出来提出去让 OCR 读**（[D-全局-45](../../20-决策记录/全局.md)）：**一局一次**、结果落盘，**识别链本身仍然是离线的**。

**那条"不上通用 OCR"的规矩只对数字成立**：数字走固定字形模板是对的（`0-9` 加小数点、模板少、可离线复现）；**汉字的字形表要几百个模板、每版本还可能变**，所以走 OCR 更省 —— 代价要认下来：**它是一次云调用、结果不可位复现**，所以只在"建库"这一步用，而且**必须落成文件**（网打在落成的那一份上）。**指纹的键仍然要人填**（用户裁定）—— 名字那个键现在不用了。

**但 `启动` 那一帧不能替掉「开局第一眼点名」**（用户确认）：**备战席的卡片顺序不按编队界面的顺序**——它按费用排，而同费用并列时（[特征库](特征库.md) §1 那个 `7/10/10/14`）**推不出来**。所以是**两件事、同一次机会**：

| 谁 | 什么时候 | 干什么 |
| --- | --- | --- |
| `启动` 顺手截图 | 开战前 | 采**本局队伍的卡面**（建库 / 补库） |
| **人点名** | **开局第一眼** | 建立**这一局的「第几张卡 ↔ 谁」**映射；**遇到没注册过的组合顺手注册** |

**人本来就盯着备战席**，所以点名时把新组合的键一起填了，不多花动作。

**而点名还有一路是自动的**（用户给的，T5 之后补进来）：**拿编队界面的卡片形象与备战席上的卡比对** —— 比中的就是那个干员，**比不中的就不是干员**。所以人的负担进一步缩小到"自动认不出来的那些"。

**为什么需要这一路：备战席上不一定都是干员。** 有些干员的技能或职业特性**自带装置**，那种干员上场之后**装置会在备战席里多占一个位置**（用户确认，[视觉层/备战席](../视觉层/备战席.md)）。于是：

- **卡数 ≠ 队伍人数 − 已下场人数**；
- 一张卡可能是**装置**，而装置**不在队伍里** —— 拿队伍去对是永远对不上的。

**所以"卡面"这份资产要多一样参照：编队界面上的卡片形象。** 它从哪一帧取还没定 —— 编队界面在 `启动` 之前，而[开题状态](../../00-总览/开题状态.md) A5 划的界线是**不做配队**，所以那一帧**得由人在配队时顺手抓**（每次队伍变了抓一张），不是工具导航过去截的。

**顺带白拿一条**：那一帧上就是**本局队伍与每张卡的样子**，所以它同时是**前提头校验的证据**——轴声明的队伍、精英化、皮肤，在那一帧上对得上不对得上，一眼可比。

### 编队页的卡片坐标（实测，原生 2800×1260）

| 项 | 实测 |
| --- | --- |
| 卡左缘 | **470 + 271k**（`k` 从 0 数） |
| 卡距 · 卡宽 · 缝 | **271 · 262 · 9** |
| 卡里那块**立绘画** | **214 宽**（右边 48 px 是卡底纹） |
| 上行（6 张）y | 137–617（**480** 高） |
| 下行（5 张）y | **642–1122**（**480** 高，两行一样高；行距 505） |

**这一组常量住在产卡面那一侧**（`assets_gen`），**不进 `UiLayout`** —— 理由是它**只在 `启动` 那一刻用一次**，线上识别链一次都不读它（见[视觉层/备战席点名](../视觉层/备战席点名.md) §判据的形状）。

**常量里那份张数是"示例帧"的，真正切几刀由清单给**：上面这张表记的是**仓里那份示例帧**（6 + 5 = 11 张）；清单 `geometry.rows[].count` 说几张就切几张（不传就照示例），常量仍钉**上下缘 · 左缘 · 卡距 · 卡宽 · 缝 · 立绘宽**，张数只留三条硬边界（两行 · 整数且至少一张 · 装得下画布）—— 一局的编队页是 5 + 5（10 人）时，两帧的坐标常量**同值**（[D-全局-38](../../20-决策记录/全局.md)）。

**`214 ÷ 204 = 1.049`** —— 这就是"两侧同一像素尺度"的那个比，也是身份区取窄之后**尺度要搜哪一段**的由来（区间住 `roster.IDENTITY_SCALE_MIN`–`IDENTITY_SCALE_MAX`，取值不在规格里抄）。

## 2 为什么不从"全量干员列表"采

**因为一局只需要一个队伍**（[特征库](特征库.md) §1 的候选集）：

- **"已选好的队伍"就是本局队伍**，卡片**位置固定** → 规则匹配，**不用滚动、不用分页、不用筛选**；
- 全量列表要处理滚动与分页，还会采一堆这一局用不到的干员。

**而且这个触点是最小的**：它不新增导航——`启动` 本来就是"开始这一局"的那一下（[开题状态](../../00-总览/开题状态.md) A5 划的界线：**不做选关、不做配队、不做重进**）。

## 3 累积，不重采

**卡面按"遇到过就留一张"累积**：同一个（干员 × 精英化 × 皮肤）第二次遇到直接命中，不再要人注册。指纹同理——"用到哪个干员就补哪个"。

**所以人的负担只跟"新出现的组合"成正比，不跟局数成正比。**

## 4 未注册的组合：不阻塞这一局

`启动` 时若发现本局队伍里有**未注册的卡面**：**照常开战**，在**开局点名那一步**提示人补注册即可——身份已经由**点名**给出，库缺一张不影响这一局。

**库的意义在后面**：备战席顺序被**不是我们的动作**改掉时（天赋重排、召唤物卡片冒出来），要靠**认卡面**重新锚定（[特征库](特征库.md) §1）。所以缺一张的代价是"**那一次重锚锚不上**"，不是"这一局没法打"。

## 5 打戳

**没有戳**——键本身就是标识。游戏改数值时靠**冲突上报**发现（数据库说一套、实测说另一套），不靠版本比对（[特征库](特征库.md) §4）。

- ~~"编队页的卡"与"备战席的卡"是不是同一款美术~~ —— **已实测：是，同一款、同一像素尺度**（原生帧上复量过；身份区取法与判据空档见[视觉层/备战席点名](../视觉层/备战席点名.md)）；
- ~~编队页的那一帧要原生分辨率~~ —— **已有原生 PNG，坐标也量了**（§1 末那张表）；
- **库与战斗帧可以不同源**（库按设计是跨局累积的）→ 所以**样本集必须写明编队页那一帧与战斗帧同不同源**。这条**没有机器检查**，只能靠写清楚；不写，下一个人会把"库里没这个人"读成"方法不行"（T5 就是这么错的，见[视觉层/备战席点名](../视觉层/备战席点名.md) §已实测 末）；
- **召唤物与装置**：它们开技能才冒出来，**不在编队页里** → 仍只能战斗内采（[特征库](特征库.md) §1）；
- **注册的入口形态**：在哪填、工具怎么提示——**未注册不阻塞这一局**已经定了（§4）。
- **§1 末那张表里的数只有"自洽约束"，没有像素网**：`left0` · `pitch` · `card_width` · `gap` 与两行的上下缘，现在由两道**互相印证**的闸门守着（清单↔常量 · 规格表↔常量），而**互相印证只挡漂移、挡不住两边抄同一个错**（[D-全局-27](../../20-决策记录/全局.md)；那个四层网全塌的实例在 D-全局-25）。
- **"能不能从画面钉住"这件事只量过一半，而用错方向就不是证据。** ① **上下缘：量过，结论是"不行"** —— 把每一行与下一行的灰度落差在全卡行上取平均、再挑最大的那些，挑出来的是 `136 / 607 / 641 / 1156 / 1175`：上缘那两条**确实在里头**（136 与 641 分别贴着 137 与 642），**两条下缘不在**（617 的落差 47.66，607 却有 82.44；1122 只有 25.53，被下面那条队名栏的 1156 / 1175 压过去）。**别照着"取最强边"再试一遍。** ② **左右缘：量过一次，但口径有循环风险** —— 在 run-03 那两帧编队页上量到：两行第 1–5 格的**左缘与右缘都落在 `470 + 271k` / `470 + 214 + 271k` 附近的最强列向边**上，而第 6 格（`470 + 271×5`）**不在其中**。它支持"这一帧是 5 张"，但**拿常量算出来的列去钉常量是循环**，所以这只能当**旁证**，不是"从画面钉住"。真要开这张单，下发的是**要求**（"从画面找出左右缘所在的列"），**不是那几个数** —— 那几个数就是 `left0 + pitch · k`，是**从常量算出来的**，拿它们去钉常量是**循环**。
