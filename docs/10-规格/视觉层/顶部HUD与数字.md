**三条边界**（这里都不重复）：

- **语义**归[状态层/全局与HUD](../状态层/全局与HUD.md)——"这个数是什么意思、允许什么形态、怎么降级"；

- **备战席卡片上那个数字**归[备战席](备战席.md)。

这里只管**ROI 开在哪**。

## 坐标口径

- 一律**捕获分辨率下的绝对像素**，**不缩放、不归一化**（[契约层 §2](../契约层/几何.md)：画布就是捕获分辨率本身）。**这台设备实测是 2800×1260**（vivo V2338A，`wm size` 报 1260×2800，横屏即 2800×1260）；
- **比例守恒，所以旧的测量能换算过来**（用户裁定）：那批 1920×864 的实例图是等比缩小的副本（×0.6857），而**同一套 UI 在两边的相对位置一致**——已验三处：`剩余可放置角色` 行左缘 1688 × 1.4583 = **2462**（原生实测 2462）· 费用条 y 648 × 1.4583 = **945**（原生实测 945–958）· 备战席卡行 715/863 × 1.4583 = **1043/1259**（原生实测 1040/1259）。换算比 **1.4583 = 2800/1920 = 1260/864**；
- **但换算只是"够用"，不是"首选"**：它把测量的误差一起放大（软边 ±13 px → ±19 px）。**能直测的就直测**（真机通路已通，取像走原始 RGBA，[设备层 §4](../设备层.md)）。下表逐条标了**原生直测**还是**比例换算**；
- 常量住 `UiLayout`（名字 → 像素矩形），**不进资产端口**（[契约层 §5](../契约层/端口与错误.md)）；
- **常量是「够用的窗口」，不是「精确边界」。** 软边的东西（菱形轮廓、卡框、顶部暗带）**同一个元素两次读数能差十几像素**——"精确边界"在那类东西上**根本不存在**。所以一律**外扩**，取一个够用的窗口：ROI 多切几像素无害，注入点取窗口中心。窗口之间**允许重叠**。

## 每个区域必须知道的事实

这些是"定 ROI 时会踩到"的事实，不是数值。

**费用数字**：**水平居中于 x≈2721**——31 帧实测中心落在 2720–2722.5，**固定的是中心、不是宽度**：1 位数宽 39–42 px、2 位数宽 74–91 px（`1` 这个字形窄）。所以窗口取**并集**（x 2676–2766）再外扩，`cost_digits` 就是这么来的。位数范围 **1–2 位**（触顶时是 `99`）。笔画高 **57–59 px**。

> **「1–2 位」的前提是费用上限 ≤ 99。** 上限可以超过 99（主线有过，合约没有）——那种局面下**报读不出，不许把三位数截断成两位**：截断就是让"不知道"伪装成"知道"。上限是[时序层](../时序层.md) §3 前提头的一项，读数链按它判"这个窗口够不够"。

**「居中」不只是描述，是判据。** 位数是**数有几个字形**数出来的，所以**缺了一位的两位数会长得像一个更短的一位数**——这是这条链最危险的一种假事实（费用是所有部署的闸门，把 `10` 读成 `1` 就是灾难）。所以**只读到一个字形时，必须回头验它落没落在中心附近**：

- **中心取 `cost_digits` 窗口自己的中心**（`x + 宽 ÷ 2`），不另立一个常数——ROI 一挪判据跟着挪；
- **判据 ±8 px**。31 帧实测：真读数的中心偏移全在 **−1.5 … +1.0**（两边各留 6.5 px）；缺一位时偏移**最小**的那一路是**首位缺失**，只偏 **15.0 px**（`shot05/19/23`，都是 `11`——两个 `1` 都窄），末位缺失在 **16 px** 开外；
- **偏了就报区间，缺在哪边由偏移的符号给**——别一律报未知，那会丢掉"我们知道剩下那一位是几"：
  - **偏左** → 缺的在它**右边** → `1?` → **`[10, 19]`**；
  - **偏右** → 缺的在它**左边** → `?1` → **`[1, 91]`**（候选是全部十个数字，区间取这十个候选的首尾）。

> **±8 不是拍的**：真读数与缺位之间那条空档是 `1.0 … 15.0`，取它中段。**若取 15，首位缺失那一路的余量是 0 px** —— 判据正好压在观测值上，换台设备或换一帧就会静默塌成一个更短的确切数。

> **这条判据只管「只剩一个字形」。** 中间少一位时块数不变、中心也几乎不偏，抓不住——1–2 位的费用不可能出现这种情况，但**将来别的读数链复用这套时要另行处理**。

> **只剩一块、而且这一块也认不出**（分数低于阈值）时：两个位置都取全候选 → **`[0, 99]`**。这是最保守的落法——我们知道少了一位，但不知道少的那位和剩下那位分别是几。

> **这几个数（`8` · `190` · `117` · `94` · `160` · 位数上限 `2`）住在代码里，规格这边把它们钉住**：`tests/spec/cost_spec.py` 的 L6 断言 `cost.py` 的同名常量与上面这几个值相等。**同一个数不许只在文档写一遍、代码写一遍而没人比对** —— 改一处忘一处就是静默漂移，`check_docs.py` 抓不到（它只看状态行 / 链接 / 废词）。

> **这一条是复量后改的**：原值 `(2665, 873, 2745, 931)` 的**右缘把两位数的末位切掉了 21 px**（并集到 2766）——是规划者自己写错，不是执行者的读数问题。

**费用进度条**：**白色填充从左往右涨**，白色部分是**已经走完的**，右边未填充的那截（到**轨道右端**，不是画面右缘）才是**距离下一点费用还差多少**（用户确认）。**未满时条上没有字**；**满时条上写 `MAX`**。

**判据分两级，顺序不能换**（31 帧实测；「每列最亮」= 该列里 `min(R,G,B)` 的最大值）：

1. **先判「自左端起有没有亮白填充」**：**最左那一列必须"基本亮"**（**≥160** —— 这条线落在一条空档里，见下）。**多列投票不许自己造出填充**：最左列暗就不是填充。
   - **有** → 数**自左端起连续亮白**（每列最亮 **≥190**）的列数 `n`（`0 < n ≤ 153`）→ `Exact(n)`。**整条亮白就是 `n = 153`**（实测 6 帧）；
   - **门开了、但一列都没到 190**（`n` 会是 0）→ `Unknown()`。**不许报 `Exact(0)`** —— "门开了"与"整条暗"是两件事，报 0 等于把"左端有东西、只是不够白"说成"我看清了它是空的"；
   - **门没开** → 进第 2 级。
2. **再看轨道本身有多亮**：
   - **满**（整条中间灰 + 白 `MAX`，每列最亮 **≥117**）→ **`Unknown()`**；
   - **空**（整条暗，每列最亮 **≤94**）→ `Exact(0)`；
   - **既不全暗也不全灰** → `Unknown()`（**没见过**的样子，报 0 等于说"我看清了它是空的"）。

**每一级各自建立在什么统计量上，是实现的自由**（那就是「形状」）——但**必须满足下面「判据的形状」那四条**。

**实测三簇，两条空档**（**注意：这是「列值」的簇，不是「帧」的簇** —— 72–116 里的观测值全部来自**填充帧的软边列**，判据走到第 2 级时那一段一个值都没有）：

- 暗 **47–73**（面板底色横向渐变；录像通道把它抬 3–4 格）· 灰 **117–189**（满态的轨道灰 + `MAX` 那几个字的边缘）· 白 **197–255**（亮白填充）；
- **190**：190–196 这一段在**原生**帧上一个观测值都没有（118–197 之间任何一个数都给同一组填充数）；
- **94**：暗簇上界 73、灰簇下界 117，**94 是这段空档的中点**。**原先取 70 —— 那是"刚过暗簇上界"，不是"在空档里"**：离暗簇的中位数（67）只有 3 格，于是「空」的余量也只有 3 格；
- **160**（**最左那一列**用的线，与上面两条**不是同一批观测**）：非填充的**列 0** 实测到 **131**（压暗的满条），被污染过的填充**列 0** 低到 **188**，所以这条空档是 **132–187**、**160** 是它的中点。

> **160 与 190 是两条线，别合并。** 190 判的是"**这一列算不算填充的一部分**"（白簇的下界），160 判的是"**填充有没有从最左端开始**"。合并成一条会二选一地坏掉：取 190 则被污染到 188–189 的列 0 会让**整个填充消失**（录像通道 48 帧实测如此）；取 160 当"亮白"线则会把**满态的灰轨道（117–189）**数成填充。

> **为什么必须分两级，不能合成一句话。** 满态与空态在"有没有自左端起的亮白填充"这个判据下**长得一模一样**（都没有），所以满态只能靠"轨道本身有多亮"来分。但**整条填满时轨道每列也是亮的（197–255）**——若先按"轨道最暗列 ≥117"判满，那 6 帧填满的会被误判成满态，**全长 153 就永远读不出来**。所以**先判"左端起有没有亮白填充"，再判"轨道亮不亮"**。

> **两个"看起来满了"的状态不是一回事**：**整条亮白（`n = 153`）**是这一秒快走完了，**相位照样可读**；**整条中灰 + 白 `MAX`** 才是**封顶**——费用到上限了，没有"下一个费用点"，相位无意义，而且**费用这条钟也停了**（[时间基](../../30-专题/时间基.md) §3.5）。

> **满态报 `Unknown()` 而不是报"满"**：契约层的载荷只有六种，塞不下一个"满"字；而且相位在满态本来就没有意义（费用到顶了，没有"下一个费用点"）。**触顶这个信息由费用数字给出**（= 前提头里的上限，[状态层/全局与HUD](../状态层/全局与HUD.md) §当前费用）。所以读数链的职责是"**不许把满报成 0**"，不是"报出满"。

> **190 与 117 这两个阈值不是"真值"，是实测三簇之间那条空档里挑的**——换分辨率、换设备都要重量。（`94` 同理，而且它**就是**这么挑的：空档 72–116 的中点。）

**判据的形状**（用户裁定）：**余量必须来自"线放在空档里"，不许靠放宽判据的形状去换。**

- 「空」看整条**最大**列、「满」看整条**最小**列 —— 那是 153 个数里的**极值**，天生没有余量。**改成看多数列**（中位数），余量就有了；
- 「有没有开始填」**必须锚在"填充自左端起"这条事实上** —— 也就是**最左那一列基本亮**。**这一处不许用"多列投票"绕开**：那会让"最左列暗、旁边两列亮"被判成填充，而那不是填充。**它的余量来自把线放进 132–187 那条空档（取 160），不是来自多看几列。**

实测三个后果：`m15b` 的 **f892–f897 六帧是同一个状态**，却因为 max 是 69 还是 71 被劈成两半（三帧 `Exact(0)`、三帧 `Unknown()`）；把空条**非最左**的任意一列涂亮会报出不存在的填充；而把**第 1、2 列同时**涂亮会报出 `Exact(3)` —— 后两个都是**假事实**。

所以：**计数**仍从窗口左端起；判据的形状**不写在这里**（那是实现），但它**必须过 `tests/spec/cost_spec.py` 的 B4 / B5 / B6 / B7**：

- **B4**：空条**非最左**的任意一列涂成亮白 → 不许报出一个 > 0 的填充数（填充是自左端起的，"第 1 列亮、第 0 列暗"根本不是填充）；
- **B5**：填充态**最左 4 列**里任意一列压到 189（刚好在亮白线下面）→ 不许变成 `Unknown()` 或 `Exact(0)`；
- **B6**：空条**中段**任意一列抬到 71（实测录像通道上"空"的上界）→ 必须仍报 `Exact(0)`；
- **B7**：空条上**任意两列一起**涂成亮白 → 同样不许报出 > 0 的填充数（多列投票不许造出填充）。

> **「满」那一级的形状在输出上不可观测**：`read_cost_bar` 的"满"支与兜底支**都**返回 `Unknown()`，所以"整条最暗列"这个极值不影响任何读数。形状照样要改，但**验收抓不到它**——别以为 B6 绿了就说明三个判据都稳了。

> **录像通道上这两个阈值不可用**（[D-全局-20](../../20-决策记录/全局.md) 换通道之后才量到）。拿同一时刻的原始静帧与录像帧跑同一条链，5 对里**填充数 4 对一字不差、台阶零抖动**，**但**：
>
> - **`BAR_BRIGHT_MIN=190` 压在观测值上**：条第 **0** 列在原始帧上 10/10 都是 **199**，而录像里 **577/1436（40.2%）落进 190–196、其中 97 帧恰好等于 190、189 一帧没有**。**余量为 0**。**但"自信地报错值"这个后果一次都没发生**：实测那 48 帧（`m15b`，第 0 列 188–189 而条体 247–255）落进了兜底支、报 `Unknown()`——要落成 `Exact(0)` 得同时满足"填充只剩 1–2 列 **且** 第 0 列掉下 190"，现有产物里一次都没有；
> - **`BAR_DARK_MAX` 被系统性抬穿**：空条暗簇上界原始是 `67`、录像是 **70（`m15c`）/ 71（`m15b`）**，于是空条大量读成 `Unknown()`。方向保守，但**"空"这个锚没了**。**所以它从 67 直接挪进空档：70 → 94**（落在空档 **74–116** 里，两侧留 **21 / 23**）——`m15c` 与 `m15b` 的空条**全部**回到 `Exact(0)`，而且余量从 **+0 / −1** 变成 **+27 / +27**；
> - **上面那句"两条空档"在录像通道上不成立**：第一条（69–116）从 0.021% 涨到 **13.894%**，第二条（190–196）从 0.000% 涨到 **0.263%**，灰簇从 7.337% 掉到 0.001%。
>
> **190–196 这个空档在两段录像里全在第 0 列**（`m15b` 297 次、`m15c` 577 次，别的列一次都没有）——那一列是条与左边界的交界，受编码影响最大（**根因已查明：它是渐变列，见上**）。**但它不是"只在第 0 列"的定律**：满态那条录像（`probe_m15`）里，同样的 190–196 出现在第 **106 / 119 / 131** 列（`MAX` 那几个字的抗锯齿边缘），1895 次——**无害**，因为计数是自左起的，满态时第 1 列只有 140–147。所以**修法不是把 `BAR_BRIGHT_MIN` 往下挪**（往下挪会撞上满态灰簇的 189），而是**给最左那一列一条落在空档里的线**（`FILL_START_MIN = 160`，见「判据的形状」）。**T3.1 当时的诊断「第一级判据不许只看第 0 列」已被 T3.4 推翻**：第 0 列不是不能用 —— **填充本来就自左端起，那一列正是唯一该看的地方**；它坏在**线压在观测值上**，不坏在"只有一列"。
>
> **顺带一条与阈值无关的**：`read_cost_bar` / `read_cost_digits` 有 `isinstance(frame, Frame)` 的闸门，**鸭子类型会被拒**——所以"把录像帧喂进读数链"只能构造真 `Frame`（`__post_init__` 只查 dtype 与 shape）。这条要写进视觉层的入口说明。

- `MAX` **不单独立常量**（它是条上的一段文字），**也不是一个独立可读的项**，理由如上；
- 这条是**连续读数，比整数费用细一档**：轨道 **157 px** 宽（原生），一个费用点 **30 逻辑帧**，所以 **1 px ≈ `0.191 / r` 逻辑帧**（`r` = 自然回费速率，**不是常数**——[时间基](../../30-专题/时间基.md) §6）。它在[状态层/全局与HUD](../状态层/全局与HUD.md) 里已经是「当前费用」的**小数部分**（进度条相位），用在这里。

> **窗口不是轨道本体（规划者复量，14 帧）**：填充的**左起全强度列是 x = 2590**、**右端是 x = 2746**——所以窗口左边多含 1 列、右边少 5 列，**轨道 ≈ 157 px，不是 153**。x = 2586–2589 是一条 4 px 渐变沿（面板底色 → 轨道色），而**窗口的第 0 列（x = 2589）正落在这条沿上**：
>
> | 状态 | x = 2590 起（全强度） | x = 2589（窗口第 0 列） |
> | --- | --- | --- |
> | 填充（u1 / u2 / p1 / p2） | 255 | **199** |
> | 满态灰轨（`m4_native` · `m3_still` ×4 · `m3_t` · `m4_native_nc`） | 146 | **118** |
> | 0.7× / 0.5× 的同一列 | 146 | **104 / 88** |
>
> **一个根因，三个症状**：录像通道上第 0 列掉到 188–189（**填充整段看不见 48 帧**）、降档后掉到 104 / 88、满态 `BAR_FULL_MIN = 117` 只剩 **1 个灰阶**余量——**都是这一列**。**而第三条在输出上不可观测**：`read_cost_bar` 的"满"支与兜底支**都**返回 `Unknown()`，所以那 1 个灰阶不影响任何读数（修完满态余量从 +1 变成 +29，三档两条通道的读数**一个都没变**）。修法是"**判据建立在全强度列上**"（已做：第 0 列的判据值取第 1 列），**窗口不动**（用户裁定）——窗口一挪，`n` 的上限就从 153 变 157，而 `n` 的口径被 31 帧夹具钉着。
>
> **连带两个数**：① 上面那个 `1 px ≈ 0.196 / r` 是拿**窗口宽度 153** 算的，按**轨道 157 px** 应是 **`≈ 0.191 / r`**；② **`n` 的上限是窗口给的 153、不是轨道的 157**——整条填满时 `n` 在 x = 2741 就饱和，**最后 5 px（约 `0.95 / r` 逻辑帧）读不出来**。这是"窗口不动"的已知代价。

**顶部条带上并排的两个数（已击杀数 / 敌人总数 与 蓝门血量）搬到[顶部两个数](顶部两个数.md) 了**（T7 拆的：事实够独立成篇，而本文件顶到 200 行）。本文件只留一条：**它俩与费用不同位**——生命与敌数在顶部，费用在右下。

**顶部条带**：**不是等高条**。两侧在 y≈26 就**羽化淡出**，中段（敌数 + 横幅）一直压到 y≈72，而且过渡是**羽化不是硬边**。所以**没有「UI 高度」这个常量**——羽化过渡不是边，硬给一个数就是假事实。谁要 UI/战场分界，谁按自己的用途切具体矩形。

**速度键**：**不进常量**。用户已裁定**不做 2 倍速**，我们从不去按它；而且它**不一定存在**（有一张实例图右上只有暂停键）。将来若真要读它，必须按"可能不存在"处理。

**备战席**：**那一栏搬到[备战席](备战席.md) 了**（T5 之后它越写越大，而本文件顶到 200 行）。本文件只留一条：**费用牌在每张卡的上边缘**（"每张卡当前费用"这个读数在这里），**卡片怎么排、位置怎么读、怎么点名都在那边**。

## 尚未定

- **`cost_bar` 窗口不挪**（用户裁定）：保持 `(2589, 945, 2741, 954)`。理由是 `n` 的口径被 31 帧夹具钉着，而挪了只多买到顶端那 5 px。**代价已记在上面**（`n` 的上限 153、最后 5 px 读不出）。**"窗口就是轨道本体"这个说法本身已被推翻**，所以将来若要挪，连带要改的是那张逐帧填充表 + `TRACK_PX` + 满态值；
- **判据的形状**（T3.4 定型）：**「有没有填充」只看窗口第 0 列 ≥ `FILL_START_MIN`（160）** —— 填充自左端起，所以那一列正是该看的地方；**它的余量来自线落在空档 132–187 里，不是来自多看几列**。「空」看**整条中位数** ≤ `BAR_DARK_MAX`（94）**且**最亮列 < 117；「满」看**整条中位数** ≥ 117 **且**最暗列 > 94。两条录像 3354 帧上**假事实 0、`n` 不符 0**。**但「空」的余量是阈值给的、不是形状给的**：暗轨道的中位数到 67，而阈值原先钉在 70 —— 余量只有 3；挪进空档（94）之后是 27。**形状解决的是"一列异常"，阈值解决的是"整段偏亮"，两者不能互相替代**；
- **一段已解释、但阈值改不动的观测**：`probe_m15b` 的 **f679–f689（11 帧）**，条的全强度列**均匀**读 **156–176**（块内标准差 1.2–2.2、没有台阶），第 0 列 131，费用数字 41。**状态是"整屏被压暗到 ~0.65 的满条"**（255→166 与 199→131 的比例都是 0.65–0.66；它落在满平台里、翻圈点在下一帧）——但 `BAR_BRIGHT_MIN=190` 是**绝对**阈值，所以第一级必然判"没有填充"，读 `Unknown()`。**这是绝对阈值对"整屏变暗"的天然失效**，与形状无关；要治得让判据**相对化**（拿画面里一个已知亮元素当参考），那是另一件事。**注意它与暂停灰罩不同**：暂停只压暗战场层、HUD 一个像素都不动（[控制层/识别时机](../控制层/识别时机.md) §4）；
- **「只有第 0 列亮」现在读 `Exact(1)`，风险方向反过来了**：填充是自左端起的，所以"只有第 0 列亮"**既可能是真的填了 1 px、也可能是第 0 列被污染到 160–187** —— **这两件事在像素上无法区分**。T3.4 之前的形状选的是"稳健"那一侧（读成 0），代价是每圈开头那 1 px 丢掉；**现在选的是"亮就算填充"那一侧**，代价是**若第 0 列被污染到 160–187，就会伪造出一个 `Exact(1)`**。实测三条录像 3354 帧里**第 0 列落进 132–187 的一帧都没有**（非填充 ≤131、被污染的填充 ≥188），所以这个风险**被那条空档挡住了，但没有被证伪** —— 换台设备、换个编码器就可能进来。**这正是空档要留够宽的理由**；
- **余量的"灰阶数"跨线不可比**：`filled > 0` 的置信度取的是 `min(第 0 列 − 160, 计数边界 − 190)`，但**这两条线坐在宽度差一个数量级的空档里** —— 160 坐在 132–187（宽 55），190 坐在 190–196（宽 7、低侧离灰簇上界 189 只有 1 格）。所以"+28 对 160"与"+28 对 190"**不是同一件事**。置信度按契约层只是「无量纲的连续量」，这里就当**粗指示**用，不当概率；
- **`BAR_BRIGHT_MIN = 190` 的低侧余量只有 1 格，但它在计数这一路上够用**：灰簇上界是 189，而**计数只在门开了之后才跑**，门要求最左列 ≥ 160 —— 满态的灰轨道（列 0 实测 **118**）永远进不来。所以那 1 格不会让满态被数成填充。`m15b` f1022–f1025 那个 **+2** 是**全条最暗列（列 0 读 192）**对 190 的余量，**只影响置信度、不影响读数**（`FILL_GAP_TOLERANCE` 会把那一列吃掉，`n` 仍是 153）；
- **备战席卡距**：**是不是随卡数变**没答（见上：5 张卡那一档是 207.5，而"12 格 530→2800"指向 189.2，口径不明）。量到之前卡框只在 5 张卡那一档成立。**"标量住哪"与"逐张卡框"两条已经在上面定掉了**（`UiLayout` 只放最右那张卡的矩形，卡距是设备层的常量）；
- **`MAX` 要不要单独可读**：判定"费用触顶"仍然靠数字是 `99`；读数链只保证"**不许把满态报成相位 0**"（见上表）。要不要让"满"成为一个独立可读的项，等状态层提出需求再说；
- **有两帧轨道整条是暗的、没有填充**（`shot18` / `shot32`）：按上表就是相位 0，但 27 帧里正好撞上两次，比"相位均匀分布"该出现的次数多。**是真相位 0，还是条在那两帧被别的东西盖住**，等读数链跑起来再判——读数链**要么报 0、要么报未知，不许猜一个中间值**。

## 真机复量清单

**这些现在都能量了**——真机通路已打通（vivo V2338A，2800×1260，取像走原始 RGBA，见[设备层 §4](../设备层.md)）。下面这些**必须在真帧上量、不许从缩小副本搬**：

| 什么 | 为什么不能搬 |
| --- | --- |
| **软边几何**：卡框 · 职业图标方块 · 顶部暗带下边缘 · 菱形轮廓 | jpg 把 2–4 px 的过渡糊得更宽，读数取决于"眼放在过渡的哪一点"——同一个方块两次差 13 px |
| **低对比颜色**：生命值的粉与其背景 | jpg 的色度子采样对**低饱和色**偏移最大，而这两个值只差一倍亮度，偏移足以改变"能不能分开"。**已经量了**（T7）：原生是平的 `(255,120,120)`，缩小副本上那个 `(104,44,54)` 是错的——见[顶部两个数](顶部两个数.md) |
| **半透明底下的"背景色"** | 它**不是 UI 自己的颜色**，是"半透明黑 × 当时那一帧画面"的乘积，换一帧就变——**不是常量** |
| **笔画宽**（量到 7–8 px） | 振铃会把它撑大，png 上可能是 6–7 px |

**可以搬的**：硬边外框的位置（误差 ±2 px 已大于 jpg 带来的偏移）、**饱和极值颜色**（白字 `(254,255,255)`、菱形里的黑 `(1,2,4)`、备席费用牌底 `(18,17,15)`）、**笔画高**（约 40 px）。

**一个必须记住的坑**：读数用的拼图若被缩放，坐标会整轮偏掉（曾经把数字高读成 26 而不是 40）。量具输出一律压到长边约 1500 px 以内，**量之前先断言图就是 1920×864**。
