# 首轮探索

> 状态：讨论中 ｜ 定位、时间对齐、**前端形态**已立；几处细则待定（§7）

**这是项目里第一个给人用的东西。** 其余全部是给 AI 用的（算子面 · 抽象层 · 暂停契约）——它不接 AI、不驱动游戏、不进在线链路，[概念 §2.2](../../概念设计共识.md) 那 14 条行为契约**一条都不适用**。

它同时就是[开题状态](../../00-总览/开题状态.md) C2 要的那个**记录器**：首轮探索那一趟，**人打一局、工具录一段、打完离线分析**，产出**资产**（地形 · 路线 · 背景帧 · 卡面）与**记录**。

## 这份目录负责什么

一趟首轮探索里，人怎么把资产做出来：**什么时候动手 · 拿什么当输入 · 什么由工具搬 · 什么必须人判断**。

## 1 定位：它是「人机入口」，不是新模块

它不是 `10-规格/` 里那 9 个模块之一，而是一个**入口**——代码落在已有模块上：

| 它用什么 | 落在哪 |
| --- | --- |
| 离线驱动视觉层 | `engine/device/replay` + `engine/vision` |
| 编辑器与校验 | `offline/assets_gen/` |

**所以它顺带是[概念 §5.4](../../概念设计共识.md) 第 3 条那条地基约束（"视觉层必须能被离线驱动"）的第一个真实用户。**

## 2 形态：两个模式

**采资产**和**录轴**是**两个相反的目标**，所以分成两局（用户裁定 → [D-全局-13](../../20-决策记录/全局.md)）：

| 模式 | 词条 | 目标 | 干什么 | 正文 |
| --- | --- | --- | --- | --- |
| **采资产** | **无** | **怪走最远**（少放干员、放它过去） | 背景帧 · **形状**（格序列 + 停留点）· 基础出现帧 · 地形 | [出怪与路线](出怪与路线.md) |
| **录轴**（**可选**） | **目标那组** | **尽量早击杀** | **轴** · 该组合的出现帧覆盖 · 禁用格覆盖 | [录轴](录轴.md) |

**为什么必须分开**：画路线要让怪走远，录轴要让怪早死——**同一局里这两个目标互相拆台**。分开之后有三处顺带变干净：

1. **"形状不随词条变"从"我推的"变成"结构上就是这么用的"**——形状从无词条局采、被带词条局复用，**一个字不用改**；
2. **无词条局更适合放怪走远**：合约常见词条里有「**初始生命变为 1**」（[全局与HUD](../状态层/全局与HUD.md) 生命条目），而无词条局拿的是**关卡默认生命** → 能放过去的怪多得多；
3. **采资产那局的停留点天然干净**：它本来就"少放干员"，我们自己的控制最少。

**录轴可选**（用户裁定）：采资产那局完全不需要碰操作记录。C2 那条"第一个可交付物是记录器"的验收判据仍然成立（工具**能**产出轴），只是**不再是每一局都要走的路**。

### 录制 + 离线分析（两个模式都是）

```
人在手机上打
  → 工具在设备端 `screenrecord` 录一段（**取像通道**，见 [D-全局-20](../../20-决策记录/全局.md)）
  → 打完拉回，离线逐帧分析（盯几个门检测点 + 读费用进度条相位）
      → 人在录像上 seek 到某帧：点几个格画路线、顺手把怪的名字标了
  → 下一局接着累积
```

**「不是事后对着录屏做」那条裁定已被取代**（用户裁定 → [D-全局-20](../../20-决策记录/全局.md)）：实时抓的密度不够——实测 **0.9 s ≈ 1.1 FPS**，而它同时毁掉两件事（**相位积分绕圈** · **出怪窗口涨到 ±27 帧**，见 §7 与[时间对齐](时间对齐.md) §1）。

三条后果跟着改：

1. **"当前是第几逻辑帧"从录像里算出来**，不再要求实时知道——见[时间对齐](时间对齐.md)；
2. **"翻帧"变成一件工具，但它不便宜**——实测 `screenrecord` 的 **GOP ≈ 600 帧 ≈ 10 s**（20 s 录像只有 2 个关键帧），seek 到 GOP 尾部要从前一个 I 帧解 ~600 帧、约 **7 s**。所以前端**不能"seek 到任意帧就跑一次全解"**。取法：**先解一遍建索引 + 一条 ~1 FPS 的缩略图带**（几百 KB/局），时间轴在缩略带上滑动，**精读某一帧时才从最近的 I 帧全解**。真需求仍是**出怪时刻的自动定位**（人掐不了表）；
3. **人的工作集中在打完那一段**，但**跨局累积照样是硬需求**（[出怪与路线](出怪与路线.md) §3）——画到一半可以留着，下一局回来再补。

### 两条通道并存，各买各的

| 通道 | 买什么 | 谁用 |
| --- | --- | --- |
| **`screenrecord` 录像** | **密度**（两次之间多近）与**时刻** | 出怪时刻 · 停留点 · 操作帧 · 跟踪 |
| **原始抓帧**（`screencap` + `pull`，[D-全局-19](../../20-决策记录/全局.md)） | **像素**——干净，且**与线上同一条管线** | **背景帧**（[背景帧](../资产生成器/背景帧.md) §3.1，**硬要求**）· 出怪帧的裁图（倾向） |

**为什么不能只留录像**：录像是 **h264 有损**，而线上的当前帧是**原始 RGBA**。凡是"要和线上做减法、或做模板匹配"的图产物，走录像就会被块效应污染——**背景帧首当其冲**：它做的正是 `|当前帧 − 干净帧| > 阈值`，块效应会淹没整张掩码。

**反过来，静帧的时刻由录像给出**：原始静帧按**内容**匹配到录像里的某一帧，那一帧的时刻由**它自己的相位**给出——于是静帧不必自己承担 `Δ`，顺带**把 `Δ` 直接实测了**（[设备层](../设备层.md) §3）。

**而卡面不受影响**：它本来就是 `启动` 顺手截的一张原始静帧（[卡面与指纹](../资产生成器/卡面与指纹.md) §1），不在录像里。

### 2.1 `screenrecord` 的实测参数（vivo V2338A · 安卓 16 / SDK 36 · v1.4）

| | |
| --- | --- |
| 可用性 | `/system/bin/screenrecord`，exit 0；**录到的是真游戏画面，不是黑屏、不是只有 UI 层** |
| 分辨率 | **2800×1260**（与画布同口径，**不是** `wm size` 那个 1260×2800） |
| 帧率 | 均值 **59.9 FPS**，但**是变帧率**：487 个不同的帧间隔，6.822–27.222 ms |
| 丢帧 | 20 s 丢 **1–2** 帧（名义时长口径 2、容器时长口径 1.5） |
| 关键帧 | **只有 2 个**，`indices=[1, 601]` → **GOP ≈ 600 帧 ≈ 10 s** |
| 体量 | 20 s → **40.26 MB**（配置 20 Mbps，实测 16.1 Mbps）→ 180 s ≈ **362 MB** |
| 拉回 | 20 s / 40 MB → **1270 ms**（32.6 MB/s）→ 180 s ≈ **11 s** |
| 音频 | **没有音轨**（只有 `vide` + 2×`meta`） |
| 上限 | `--time-limit` 默认 **180 s**（`0` = 不限）；到点**正常收尾、不截断、文件完整** |
| 帧数 | **`--verbose` 直接给出权威帧数**（`recorded N frames in T seconds`），比数容器样本省事 |

> **两个数直接改掉了两条设计**：**长 GOP** 让"seek 到任意帧"不再免费（§4.1 第 2 条），**变帧率**让"第 n 帧 = n/60 秒"作废（[时间对齐](时间对齐.md) §1）。**都是"密度涨了 30–60 倍"这句话的代价。**

**但录像通道上有一条已知缺陷**：**费用条的"空"读不出来**——47 帧空条里 43 帧报 `Unknown()`（暗簇上界被抬穿一格），而"亮白"阈值 `190` **余量为 0**（条第 0 列 40% 的帧落在 190–196）。**根因已查明**：`cost_bar` 窗口的第 0 列是一条 **4 px 渐变沿**上的像素（原生读 199、满态读 118），它本来就是全条最脆弱的一列——**同一个根因也让降档后的那一列掉到 104 / 88**。见[视觉层/顶部HUD与数字](../视觉层/顶部HUD与数字.md)。

**相位本身读得出来**：5 对配对里填充数 **4 对一字不差**、整段台阶**零抖动**、满态 **399/399** 全对。所以**积分不受影响**（跨圈仍可从 `153 → 小值` 看出来），**但"空"那个锚没了**。出处与修法见[视觉层/顶部HUD与数字](../视觉层/顶部HUD与数字.md)。

## 3 人的输入里不许有「搬运」

判据的形状：**凡是"翻帧、找像素、抄坐标、抄数字、重复同一条"，都必须为零**。

| 产出 | 只有人能判断 | 工具搬 |
| --- | --- | --- |
| 地形 | 这格是地面还是高台 · 门在哪 · 这几格挂了什么机制 | 对齐格网 · 渲染叠加 · 校验不变量 |
| 路线 | 这是哪种怪 · 这条走哪 · 补全尾部 | 找出怪事件 · 跟轨迹 · 吸附格 · 算帧号 · 排序 |
| 背景帧 | 哪一帧干净 | 抓帧 · 打戳 · 按视图分份 |
| 卡面 | 每张卡是谁 | 裁卡 · 按固定位置切 · 建索引 |
| 特征库样本 | 这些是不是同一种 | 切图 · 去重 · 按类型分目录 |

**可测的代理量**：`人的输入次数 ÷ 出怪条数`（应当远小于 1——形状是共享的）与**一关的制作时长**。**数值不在这里拍**，第一次做的时候量一次就有了。

## 4 交互：三条

1. **投影标定**（每关每视图一次）：工具给截图 + 可拖格网，人对齐 → `origin / col / row`。**字符画与截图之间没有换算关系，前端就只是个贴图**——所以标定不是另一件事，是编辑器的第一块；
2. **格网叠加**：人在暂停帧上点格画路线（**主通道**），工具把点连成格序列；
3. **叠加验收**：截图 + 格网 + 地形着色 + 路线折线 + 门标记，人扫一眼——这是**零假事实落在资产上的形态**（[地形](../资产生成器/地形与关卡资产/地形.md) §3 已立）。

### 4.1 前端形态：分两步，判据是「要不要列表 + 批量 + seek」

**不是"地形用 OpenCV、路线用网页"，判据是这个：**

| 产出 | 交互长什么样 | 壳 |
| --- | --- | --- |
| **地形** | 点格子——一张截图 + 可拖格网就够 | **OpenCV 窗口** |
| **路线** | 一关几十条形状 × 每条十几个点，还要**跨局累积 · 按类型分组 · 删假阳性** | **网页** |

**两段之间靠文件对接**（那四个文件），所以分两步**不需要共享一个前端**。

**网页版的核心只有三块**：

1. **一张可点的截图**（带格网 / 叠加层）；
2. **一张表**（候选列表：改一栏、删假阳性）；
3. **一条时间轴**（seek 到某帧、跨局拼接、**看得出哪段是慢放**）。

**换通道之后它多两件事**：**解码与播放录像**（h264，栈里已有的 opencv 能解）· **录制文件管理**（拉回、按局存、与跨局累积对上）。

因为 §5 末那条已经立了：**一套形状用在三处**。

**一条容易漏的前提：人的注意力在手机上，电脑只是余光。** 所以——不弹窗、不模态、不需要读文字的确认；状态要**一眼可见**（第几帧 · 正在盯哪几个门 · 这一局采到几条）；**人的输入少而粗**，细活归工具。

**壳选「本地服务 + 浏览器」**，不是"静态页 + 预处理"：**跨局累积、画到一半**这类状态得活在工具里，而静态页面要靠反复重生成。**理由已从"边打边写"换成这一条**——换通道之后不再是边打边写，但"状态要活在工具里"没变。

**两个模式共用一个前端 + 一个模式开关**——交互形状相同、时间对齐共用，分开入口等于把同一套 UI 写两遍。默认落在采资产（录轴可选）。

## 5 与别处的关系

- **它是[资产生成器](../资产生成器/README.md) 的人机入口**：产出五样产物里的四样 + 特征库的样本；
- **它同时是 C2 的记录器**（**录轴模式**，可选）：那一趟也产出**轴与记录**（[时序层](../时序层.md) §1）；
- **它顺带白拿两样**：出怪帧的裁图就是[特征库](../资产生成器/特征库.md) §2 排队优先级①的样本；**无词条局**的开局帧就是[背景帧](../资产生成器/背景帧.md)。**这两样的像素都走原始抓帧**（§2 两条通道）。**同一个产物，两个用途**——这是"采集不单独占动作"的第三次实例（前两次：卡面挂 `启动`、难例挂识别）；
- **一套交互形状用在三处**：出怪候选 · 操作候选 · 朝向修正——都是**暂停时给一张表，人扫一眼改一栏、删假阳性**。

## 6 已定

- **两个模式分开**：采资产（无词条，怪走最远）· 录轴（带词条，尽量早击杀）；
- **录轴可选**；
- **取像走 `screenrecord` 录制 + 离线逐帧分析**（[D-全局-20](../../20-决策记录/全局.md)）——取代原来的「边打边用、不做事后录屏解析」；
- **只打合约**（用户裁定）→ **"无词条"就是"一个词条都不选"**，不存在"打常规关卡"那条岔路；而**开发期可以打「全息作战矩阵」**（常驻、模式接近老合约）—— 见 [D-全局-21](../../20-决策记录/全局.md)（原 §7 那一问因此关掉）；
- **出怪时刻自动定位**，人不掐表；允许 **±10 帧**误差；
- **时间对齐靠费用进度条相位积分**，不读余额（[时间对齐](时间对齐.md)）；
- **只有无词条局的开局帧能当背景帧**；
- **门检测点默认取门格**，被 UI 挡住时手动拖到门后一格；
- **同一条形状必须能跨多局累积**；来源只存「观测 / 推断」二值；
- **「同一形状」的判据 = 观测段能不能接上**（[出怪与路线](出怪与路线.md) §3）；
- **朝向只有上下左右四个**，不含斜向；**看不到箭头 ⇒ 朝上**，不设降级规则；**误判**靠"标记这个干员要人给"兜住（[录轴](录轴.md) §3）—— **T5 之后确认：读的时机是"部署那一刻"，那时没有特效；永续技能盖住箭头那一类按"尽力"处理，不改判据**（[录轴](录轴.md) §3）；
- **前端分两步**：地形走 OpenCV 窗口、路线走网页，判据是"**要不要列表 + 批量 + seek**"（§4.1）；
- **壳选本地服务 + 浏览器**，不是"静态页 + 预处理"（§4.1）；
- **两个模式共用一个前端 + 一个模式开关**；
- **人的注意力在手机上**：不弹窗、不模态、状态一眼可见、输入少而粗（§4.1）。

## 7 尚未定

- **`screenrecord` 的落地参数**（**通道已定**：走它，[D-全局-20](../../20-决策记录/全局.md)；参数与可用性待真机测，见[设备层](../设备层.md)「尚未定」）：`--time-limit` 要不要分段 · 目标分辨率与码率 · **编码器会不会丢帧、丢多少** · 录制文件体量与拉回耗时 · **这台安卓版本上 `screenrecord` 是否还在**；
- **字符图的图例**（哪个字符代表哪一类）：[地形](../资产生成器/地形与关卡资产/地形.md) §2 的校验器要查"每个字符都在图例里"，但**图例本身没有落成规格**；
- **出怪密集的时段要不要主动进慢放**：慢放下同样的取像周期折成的逻辑帧只有 1/10。**换通道之后这条的紧迫性掉了**（录制已是 30–60 FPS），但"要不要为判定精度额外进慢放"仍可单独定；
- **`--time-limit` 默认 180 s，而一局方舟战斗常超 3 分钟**（实测 20 s → 40.26 MB，则 180 s ≈ **362 MB**、拉回 ≈ **11 s**）。**"一局一录"和"默认上限 180 s"很可能对不上**——要**分段录制**还是**去掉上限**，待定。分段还有两个附带好处：每段起点必然是同步帧（seek 更近）· 单文件不至于过大；
- **出怪帧的裁图能不能直接走录像**：**背景帧一律走原始抓帧**（§2，硬要求）；而出怪帧的裁图只做**聚类分组**（临时资产，[出怪与路线](出怪与路线.md) §2），块效应也许无所谓，**要试**；
- **h264 的颜色与原始 RGBA 是否一致要实测**：录像经 YUV 4:2:0 → RGB，**解码用的色彩矩阵（BT.601 / BT.709）选错会整体偏色**。判据是"拿同一时刻的原始静帧与录像帧比对"；
- **§4.1 那条「人的注意力在手机上，电脑只是余光」要不要保留**：换通道之后人是**在电脑上看录像**做画线，"不弹窗、不模态、一眼可见"这三条约束的**来源变了**——是放松还是保留，待定；
- **前端的技术选型**（实现期的事）。
