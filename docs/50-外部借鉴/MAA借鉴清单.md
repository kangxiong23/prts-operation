## 二、逐条说明与自检

### 1. 定死运行环境，不做分辨率适配 ★最先

**它的问题**：用户设备的分辨率与宽高比不可控，而识别规则里全是坐标。
**它的方向**：把所有识别压到一块统一画布（1280×720）上，坐标只以该画布为单位，**非 16:9 直接拒绝支持**。代价是放弃了不合规设备，且缩放会丢小字细节。

**我们的做法**：我们本来就要选定运行环境（模拟器，分辨率固定可控）。那就不该把分辨率做成资产的**一个维度**，而应做成**环境要求**——不合规直接报错，不降级、不适配。

**自检**：价值高（省掉一整个维度的回归成本）；门槛低；复杂度低；工期极小。**结论：做，且是第一条要落地的约束。** 这条一旦定晚，资产条目数和回归成本直接翻倍。

---

### 2. 视觉原语契约：ROI + 原语种类 + 结果三元组 + 三态

**它的问题**：全图搜索慢；同一个"确认"按钮满屏都是，靠全局语义分不开；不同 UI 判断的"问法"其实只有几种。
**它的方向**：① **ROI 是一等公民**——识别被定义成"在调用方指定的窗口内回答一个问题"，窗口还可以继承、外扩、或由上次结果偏移派生；② 原语按**问什么**分而不是按底层算法分（图在哪 / 写的什么 / 同形不同尺度 / 有几个 / 颜色是否出现 / 符号是否一致）；③ 结果统一成 **`{矩形, 分数, 载荷}`**，失败用空值而非异常；④ 因为"没看"和"看了但没有"结构上无法区分，后来不得不补出**三态**。

**我们的做法**：我们的抽象战局里**每一个字段都必须能回答"在哪个 ROI、用哪种原语、置信度多少"**。同时把它的教训提前吸收：字段必须是**三态**——未采样 / 已采样且为空 / 有值。这一条和我们概念文档里"未识别必须显式上报"是同一件事，但更严格：**AI 把"没采样"当成事实，比认错更危险。**

**自检**：价值高（它同时是抽象层的可调试性、AI 的置信度来源、以及防假事实的闸门）；门槛低；复杂度低-中；工期小。**结论：做，作为抽象层的第一个接口设计。**

---

### 3. 静态先验离线化，在线只留时间相关量 ★最大杠杆

**它的问题**：排轴需要确定的格子语义（哪格可部署、高低台、门在哪），而画面里根本看不出格子边界。
**它的方向**：**逐关离线**预计算格子语义（含像素与格坐标）作为静态资产，运行时只做"格子→像素"的投影，**不做"像素→格子"的推断**。在线只识别己方（可部署列表、费用、冷却、职业、朝向）与费用、击杀数；**敌人完全不识别**，红门只是格子上的静态标签。

**我们的做法**：把它的切分原则**推到极致**，作为抽象层的第一条设计原则：

- **离线化**：关卡地形与可部署性、**场地机制**、干员身份与攻击范围、敌人波次表。
- **在线保留**：只有随时间变化的量——敌人位置与血量分档、技能 SP、费用、我方干员状态。

这对我们有一个直接的政策含义：**你此前确认"场地机制也必须识别"是对的，但"识别"不等于"每帧从画面认"。** 场地机制绝大多数是**静态的**，可以逐关离线和首轮记录一起固化下来。这样既满足"必须知道场地机制"，又把最贵、最容易因特效而失稳的那部分识别负担从在线链路里拿掉了。**这条与第 5 节警告（2）互为解药。**

**但"静态"有一个例外，必须建模进去**：存在"掀地板"类敌人技能，会在战斗中把可部署地块变为不可部署（目前尚未出现在合约里，但机制存在）。因此地形**不能建模成不可变常量**，正确形态是「**离线提供初值 + 在线只监测增量**」——在线那部分是一个**变更检测器**（某格从可部署变为不可部署），远比"识别地形"便宜。而当它真的发生时，AI 的计划会直接失效，所以它必须作为**事件上报**，并与第 6、8 条联动。

**自检**：价值高（这是唯一能实质压低我们识别风险的手段）；门槛中-低（见第七节实测：逐关几何由脚本全自动生成、人工只做例外 patch，新增一个活动的人工增量约 50 行可套模板的 JSON；我们本来就有"人工首轮经工具记录"这条流水线，资产可以作为它的副产品产出）；复杂度中；工期中。**结论：做。它是本项目性价比最高的一件事。**

---

### 4. 按需声明本次识别哪些字段

**它的问题**：战斗里可看的项很多，而单个决策只用得到一两项；全量识别又贵又扩大误判面。
**它的方向**：识别接口收一组"本次要哪些字段"的开关，只算被要的部分，其余字段留在结构里不填。代价是逼出了上一条的三态问题。

**我们的做法**：我们有一个它没有的强约束——**暂停条件必须由工具常驻判定**。如果每个条件都触发全量战局识别，常驻判定在算力上直接不成立。正确切法是：**暂停条件声明它依赖哪几个字段，工具只对这几个字段做高频判定，其余字段按需即时计算。**

**自检**：价值中-高（它其实是"常驻判定可行"的前提，不是纯性能优化）；门槛低；复杂度中；工期小-中。**结论：做。** 但要注意它不是"能省则省"，而应与暂停条件的字段依赖绑定设计。

---

### 5. 离线重放器作为抽象层的验收手段

**它的问题**：怎么证明识别、阈值、区域是对的，而不是"看着还行"？怎么复现用户反馈？
**它的方向**：把本地截图喂进**与线上完全同一条**预处理 / 模板 / OCR 链路，产出命中项、匹配得分、OCR 原文，并能按任务链逐图重放；配套取色、掩码、区域生成、坐标标注等小工具。**关键纪律：文档里显式声明这个复刻器与线上有哪些不一致**（缓存、候选筛选等），否则结论会错。

**我们的做法**：这正好回答了我们概念文档里的开放项——"抽象层的正确性由谁保证"。它比我原先写的"交叉自洽校验"硬得多，而且可以直接当验收用。需要同时定下一条**架构约束**：**视觉层不允许与实时取像耦合，必须能被离线驱动。**

**自检**：价值高；门槛低-中（难的不是写重放器，而是让视觉层别长在实时链路上）；复杂度中；工期中。**结论：架构约束现在就定**（因为它决定视觉层的接口形状，事后补极贵）；**实现排在抽象层之后、AI 循环之前**——在没有它之前，AI 的一切结论都不可信，先跑循环等于浪费 token。

---

### 6. 轴每步带显式前置条件；失败交回 AI 而非降级跳过

**它的问题**：作者希望"等怪清完再下干员"，但工具不该去理解战场。
**它的方向**：轴是**有序动作流 + 状态门槛**：每步挂若干全局门槛（击杀数 / 费用 / 费用变化量 / CD 中干员数 / 作者自建的计时器），全满足才执行；另有前后延时与**超时**——**超时即放弃当前动作、继续下一步**。条件只有"且"，"或"至今是 TODO；全局计时器只有一个且必须显式重置；而且它**无法表达"出现意外就改计划"**。

**我们的做法**：采纳"每步显式前置条件"（这样审阅者才看得出"为何此时、不满足会怎样"），但**拒绝它的超时语义**。它的超时是降级跳过——对我们是有害的：AI 批准过的轴因为一个条件没满足就悄悄跳过一步，后面全错而无人知晓。我们的正确语义是**条件超时 → 暂停并把控制权交回 AI**。

顺带记一条定位依据：**"条件等待失败时该怎么办"这一整条缝，就是 AI 该介入的位置，也正是它能力边界外的地方。** 这是本项目存在意义的旁证。

**自检**：价值高（它保护"审批=我认可这份计划"这个语义）；门槛低；复杂度低-中；工期小。**结论：做。**

---

### 7. 轴带显式版本 + 环境前提声明 + 认不出即报错

**它的问题**：社区几万份历史作业要能被新版一直读下去。
**它的方向**：字段几乎全可选、未知动作类型**只警告并跳过**、废弃字段映射到新语义、最低工具版本由作者手写并在导入时硬校验。**代价很重：没有真正的 schema 版本与迁移，旧作业会"部分执行"，静默跳步，错了也无人知晓。**

**我们的做法**：走**相反**的路线。理由很直接：我们的轴是**被审批过的**产物，静默跳步会让"已批准"变成假的。

具体三条：
1. **轴必须有显式版本号**，新版本必须声明如何迁移旧轴，不能靠"字段可选"糊过去。
2. **认不出 / 校验不过 → 报错并拒绝执行**，不跳过、不降级、不猜。
3. **轴必须声明它成立的环境前提**：分辨率、帧率、练度指纹（精英化/等级/潜能/模组/技能等级/皮肤）、游戏版本、**合约词条**、队伍。少任何一项，"审批后重放等于复现"就是假的——因为轴对帧率、分辨率、识别误差都敏感，换设备即走样。

（第 3 条是本次分析对我们概念文档的**实质补充**：原文档只写了"词条由人选"，没有要求轴记录它所依赖的词条前提。）

**自检**：价值高；门槛低；复杂度低；工期极小。**结论：做。** 三条都是低成本、保护核心闭环的事。

---

### 8. 留一个"人工纠正工具认知"的入口

**它的问题**：干员位移后，工具内部记的坐标就错了，会导致后续"按名字开技能/撤退"落到错格子。
**它的方向**：提供一个专门的轴动作 `SetUnitLocation`，**不对游戏做任何操作**，只修正工具内部的位置记录，也可用于登记装置、设施等非干员单位。

**我们的做法**：这是条很诚实的经验——**工具对世界的认知一定会漂移，必须留一个"人工纠正认知"的入口，而不是让它带着错误认知继续跑。** 对我们尤其合适：我们的 AI **保留直接识图能力**，它正是最有可能发现"这个干员明明在 A 格，你却记成 B 格"的角色。给它一个"我告诉你实际是什么"的动作，成本极低、收益很高。

**自检**：价值中-高；门槛低；复杂度低；工期极小。**结论：做。**

---

### 9. 内容包版本化 + 事件 schema 带版本 + 横切组件走订阅

**它的三条相关做法**：
- **引擎与内容分离**：资源是带版本戳的独立内容包，引擎按固定目录装载，游戏更新不必发版。
- **横切逻辑订阅消息流**：统计、计数、存证、上报通过"任务回调 → 插件链"接入，插件声明自己关心哪条消息，而不是插进主流程。
- **对外只有一个可观测面**：所有 UI / 日志 / 调试都消费同一条消息流，内核不依赖任何界面。

**我们的做法**：三条都值得，但都要**去掉它为多平台多语言付出的那部分**：
- 特征库与轴库做成独立目录 + 版本戳 + **拒绝降级**；**不做**增量 zip、多服 overlay、多层叠加（它自己的代价就是"最终生效的是哪份定义"极难推理）。
- 我们的时间片记录器、抽象状态注入器、轴校验器都应该是**订阅者**，而不是主循环里的分支。
- 事件 schema **必须带版本号**——它这条恰恰是反例：它的消息 schema 无版本号，官方自己承认消息在飞速迭代，导致插件很脆。

**自检**：价值中-高；门槛低；复杂度低-中；工期小-中。**结论：做，取轻量版。**

---

### 10. 资产生成器 + 定时 CI

**它的问题**：关卡每周新增，人工标注跟不上且口径不一。
**它的方向**：地形、干员表、物品表等**从上游官方数据编译**，独立生成器 + 定时 CI 每 20 分钟重生成并提交；只把推不出来的（相机投影、主题变体、语言替换表）留成人工资产。代价：上游可用性与正确性不在自己手里，表结构一变流水线即断；生成物入库换来可审计的 diff，代价是仓库体积。

**我们的做法**：**原则现在定，实现推迟。** 现在就要做的是按"**可生成 / 必须标注**"来设计两份资产的数据格式——这决定字段怎么切；但第一版先手写覆盖单个关卡的最小数据把闭环跑通，生成器和 CI 等闭环成立后再补。

**自检**：长期价值高；但门槛中-高、复杂度高、工期大，**在第一版闭环尚未验证时投入它是不划算的**。**结论：原则现在定，实现推迟。**

---

### 11. 能力型编队：只取一半

**它的问题**：一份作业要在不同玩家的账号上都能跑。
**它的方向**：把"谁"与"做什么"分离——轴声明**需求与备选**（例如"任意正常群奶"，或"这里需要一个先锋"）并列出候补，练度写成可校验门槛，动作只引用组名；**执行期由工具按练度择优分配**。

**我们的做法**：只取"声明需求"，拒绝"执行期择优"。取的部分：轴记录"这一步需要什么角色/能力"，它能提升轴的可读性，也让校验器能检查"这一步的需求与当前队伍是否匹配"。拒绝的部分：**执行期择优是判断，而判断归 AI**——这直接违反我们的责任边界原则。我们的 AI 有游戏数据库和完整队伍信息，绑谁由它决定。

**自检**：价值中（可读性与校验收益真实，但我们的场景不需要"跨账号可跑"）；门槛低；复杂度低；工期小。**结论：取一半。** 这也是一次边界纪律的检验：**凡是"执行期要做选择"的设计，一律并入 AI 侧。**

---

### 12. 风险声明独立成文

**它的问题**：开源许可证覆盖不到游戏数据版权、账号风险、社区禁忌与收费边界。
**它的方向**：代码走 AGPL，**另附独立用户协议**：声明游戏数据资源版权属官方、与官方无关联、图像识别可能被反作弊误判、不承担账号损失、以及"软件免费、服务收费"的边界。

**我们的做法**：我们同样需要一份，而且要写进两件它做对了的事：**明确标注"哪些机制是随机的"**（它就是这么标注费用识别受潜能影响、三位数可能认错的），以及**资产什么时候会失效**。另外一条它没写但我们该写的：**MIT 只覆盖代码，不覆盖由游戏数据派生的资产**（关卡几何、敌人属性等版权属官方）。

**自检**：价值中（不是技术项，但是公开发布的必要条件）；门槛低；复杂度低；工期极小。**结论：做。**

---

## 三、只作为定位依据，不是待办

**1. 它的轴三件套证明了我们的时间态设计成立。** 它的动作类型里直接包含"二倍速""子弹时间（1/5 速）""重置全局计时器"——**暂停/慢放/改倍速可以作为轴的一等元素**，这不是我们拍脑袋想出来的。

**2. 它明确停在"不做战术决策"上。** 技能只有四种粗粒度用法；被问及"自动判断使用时机"时，代码里根本没实现、文档直接写"画饼"。**它主动放弃了那块，而去做了自动化刷图。** 这就是我们要占的位置。

**3. 执行器应当是确定性时序执行器，不是"识别列表取第一个命中"。** 它的任务是 JSON 里的识别-动作-后继图，靠"依次识别、第一个命中即跳"驱动；代价是图灵不完备、还长出一套需要专门文档解释的隐性小语言。我们的判断在 AI 侧，**执行器不该继承这套复杂度**——应是一个确定性的时序执行器。

**4. 它的轴本体是"一次成功通关的操作记录"，不是策略。** 它甚至有一条"从战斗录像反推轴"的实验链路，会把部署/技能/朝向/等待条件自动生成成 JSON。这印证了我们"人工首轮也走工具记录、记录本身成为起点"的决定是对的——那条路它走通过。

## 四、明确不做

| 它做了 | 为什么我们不做 |
| --- | --- |
| 多设备后端统一抽象与能力探测 | 我们只走一条取像/注入通道，抽象立刻变成纯负担。只保留"分辨率无关坐标系"——而按第 1 条，我们连这个都可以省掉，改为**强制环境合规**。 |
| 多语言 / 多区服 overlay 与任务继承语法 | 为五语言六区服而生。单服单语场景下，多层叠加 + 前缀继承会让"最终生效的是哪份定义"难以推理。 |
| 识别-动作-后继的轮询式流程引擎 | 判断在 AI 侧，见上节第 3 条。 |
| 增量 zip 资源包、不校验完整性的热更新 | 它的代价是"缺文件也能装、装坏只能手动拖包自救"。我们做轻量版：独立目录 + 版本戳 + 拒绝降级 + 校验完整性。 |
| 轴字段全可选、未知动作静默跳过 | 见第 7 条。 |

## 五、它给我们的三条警告（我们方案里可能过于乐观的地方）

**1. 它从未真的"折成完整战局"——这条最值得警惕。**
它把符号化**严格限制在离散、可枚举的空间里**（关卡格子地图，甚至肉鸽地图也是逐格判定 + 多帧投票），战斗状态只做了最薄一层。原因是**连续时间 + 部分可观测**让"完整战局符号化"的边界无法闭合。

我们的反驳必须写清楚，否则这个项目不成立：它的困难来自**通用性**——任意关卡、任意阵容、任意设备、任意用户。而我们把它缩减成**单关卡、固定编队、固定练度、固定分辨率、固定设备，且有一轮人工摸底**。**这四条约束是我们敢于做完整符号化的唯一理由。** 如果将来任何一条被放开，这一条警告就会立刻生效。

**2. "离线采样一次即可长期匹配"会低估维护曲线。**
它的 ROI、模板、文本都是**人工维护资产**，随 UI 改版与语言数持续付费；文案变长还要联动改 ROI，而且失效方式是**静默**的。**第七节的实测把这条钉死了**：它的人工资产驱动量是"含文字的模板 × 区服数"（`global/` 下 2252 个文件，主体是按区重裁的含文字模板），而**不是关卡数**。对我们更麻烦的是**带视觉特效的场地机制**——书店里的特效每帧都在动，纯特征匹配会持续失稳。

**解药就是第 3 条**：把场地机制从"每帧识别"改成"逐关静态资产"。**能一次写死的，绝不在线认。**

**3. 它没有统一的置信度传播，靠"分数 + 人工阈值 + 重试"吸收不确定。**
我们要用多来源证据合成一个抽象状态，就必须自己补这一层。它的肉鸽地图用"证据列表 + 多帧投票"是简化版，但那是**离线批量**的做法，不适合我们逐帧的常驻判定。**这是我们必须自己解决、没有现成答案的一块。**

## 六、如果只做三件事

1. **定死环境 + 归一化画布**（第 1 条）——成本极小，不定晚则代价翻倍。
2. **静态先验离线化**（第 3 条）——唯一能实质压低识别风险的手段。
3. **离线重放器作为抽象层验收**（第 5 条）——没有它，AI 的所有结论都不可信。

## 七、补充回查：资产维护成本实测

**起因**：担心"符号化本身会带来大量维护工作量——每出一个新合约就要把与地形/机制有关的静态资产重做一遍"。本节是对这个担心的实测核查，它修正了第五节警告 2 的强度。

### 7.1 它 9499 个资源文件的账本

| 类别 | 规模 | 是否随关卡数增长 |
| --- | --- | --- |
| 生成物：关卡几何 `Arknights-Tile-Pos` | 4256 文件 | **否**——CI 每 20 分钟从上游关卡表生成，人工只做例外 patch |
| 生成物：物品/基建图标、物品表、招募、掉落、卡池时间 | 约 1000 文件 | 否——同上 |
| **人工：战斗识别资产** | `template/Battle` **191 张 + 4 个模型** | **否——全部是通用 UI（技能就绪、费用、二倍速、编队、开始按钮、结算）** |
| 人工：任务链 `tasks.json` | **1100 个顶层任务 / 6927 行** | **否——按界面与机制组织，不是每关一套** |
| 人工：多区服 `global/` | 2252 文件 | 否——**主体是含文字模板按区重裁** |
| **唯一按关卡线性膨胀的** | `roguelike/*/autopilot/`（252 文件）、`copilot/`（约 75） | **是**——但 `copilot/` 就是"轴"，是产品本身，不是维护负担 |

**每新增内容的实际人工增量**：新活动 ≈ 一个约 50 行的 `Stages/XX.json`；新主线章节 ≈ 1 张图 + 1 行；新 UI 主题 ≈ 9 张图；新小游戏 ≈ 1 个文件 + 约 10 张模板。**新关卡的地形、物品图标、基建技能图标是 100% 自动生成的。**

### 7.2 它把成本压平的四个手法（都可迁移）

1. **别为"会变的字符串"做资产。** 关卡名不建模板：`ClickStageName` 的文本为空、ROI 为全屏，**由 C++ 在运行时注入关卡代号**。即：变量走运行时注入，不烘焙进识别资产。
2. **可选补丁优先于必交资产。** 关卡导航默认走通用方案（OCR 关卡名 + 滑动），只有识别不稳的活动才额外加一张模板；有模板才用，否则回退 OCR。
3. **会变的东西推到远程数据。** 当期活动关卡列表来自远程 json，**加一个活动关不改客户端代码**。
4. **变体用 key 精确取用，不搞引用叠加。** 变体靠 stageId 全串精确匹配；"引用/叠加"只存在于任务层与区服差分层。**代价是仓库体积（约 17% 重复文件），不是维护成本。**

### 7.3 它的痛苦痕迹恰好落在我们碰不到的维度上

专门的 `TaskSorter.py`（给 1100 个任务排序以稳住 diff）、`FindMissingTemplates.py` 开篇写着 "needs your help" 且维护清单要手动更新、注释里抱怨"无限池越来越多，用 roi 已经不够了"、"国服现在 ui 改了，兼容外服"。**这些全部集中在"界面种类"与"多区服"两个维度上。**

### 7.4 结论（修正第五节警告 2）

> **人工资产随"UI 与识别点种类数"增长，不随关卡数增长。**

对我们而言这个结论更强：**作战界面在所有关卡、所有合约下都是同一套**，我们不选关、不进活动页、不打小游戏、不打肉鸽，且只有一个区服一种语言。**它的 191 张通用战斗模板 + 4 个模型，就是我们这一层的量级参考——而且我们只写一次。** 唯一按关卡线性增长的是"轴"（在它那里是 `copilot/`，约 75 个、社区投稿），那正是我们的产品。

### 7.5 关于危机合约

它**完全没有支持过**这个模式：没有 Contract 类与配置、`tasks.json` 里没有相关任务、文档里没有"危机合约"、Tile-Pos 里也没有专属关卡 id。**这件事它没有经验可借。**

它的 `#f#` 经验来自**突袭**——一个固定、在数据里就存在的变体；而合约是玩家从池子里选词条的**组合式**玩法，形状不同。可迁移的只有 7.2 那套成本手法。

而**"每出新合约就要重做资产"这个担心本身可以消掉**：词条由人选定，因此一次探索会话里**词条组合是常量**，不存在组合爆炸——需要固化的只是"**实际试过的那几个组合**"，通常就是 1 个。再叠加一条更省的结构：**合约只把部分地面/高台变为不可部署**，所以地形资产应当是「**一份基础地形 + 每个词条组合一小串被禁用的格子**」，而不是"每个组合一份完整地图"。成本与**被禁用的格子数**成正比、与地图大小无关，而组合数通常就是 1。（唯一的例外见第 3 条：掀地板类敌人可在战斗中改变地形，所以在线仍需一个变更检测器。）

### 7.6 两点我们必须反着做的差异

1. **它完全没有敌方数据。** 上游 checkout 里没有 `enemy_*`，`resource/` 里也搜不到敌人表——唯一的 `battle_data.json` 只装干员字典与攻击范围（`chars` + `ranges`），是纯静态干员数据。它从头到尾不碰敌人。**但它不碰敌人是设计上不需要，不是技术上不可行**：`ResourceUpdater` 已经示范了"从官方 gamedata 生成 resource"的完整管线，敌人表据称也在 gamedata 里（**该表未被 checkout，本地无法验证，属推断**）。所以我们要建敌人库**有现成生成管线可循**，不必从零摸索。
2. **它的生成器不锁上游 commit**（每次取镜像 HEAD），因此**无法回答"这份资产对应游戏哪个版本"**。我们的轴要声明环境前提，所以这里要反着做：**资产必须带可追溯的数据版本。**

## 八、补充回查：识别稳健性与 A4

**起因**：A4（像素特征能否可靠区分画面元素）是本项目最大的技术风险，难例包括大量敌人重叠、特效把干员整个包住、遮挡、动画中间帧。本节记录它的识别稳健性设计。

### 8.1 它那 4 个 onnx 模型是什么

| 模型 | 位置 | 输入 / 输出 |
| --- | --- | --- |
| `skill_ready_cls` | `Vision/Battle/BattlefieldClassifier.cpp` | ROI 是格子中心上方的技能气泡，裁成 64×64 三通道，出 3 类（c/n/y）+ softmax，只有第 2 类判为"就绪" |
| `deploy_direction_cls` | 同上 | ROI 为格子周围 96×96，出 4 类朝向（右/下/左/上） |
| `operators_det` | `Vision/Battle/BattlefieldDetector.cpp` | 整帧缩到长边 640，yolov8，输出 `{1,5,8400}`，conf ≥ 0.3 后 NMS；**检测的是干员血条**，用来判定"已部署干员" |
| `BlackFlow_corridor_net` | `Vision/Roguelike/EdgeDetector.cpp` | 输入相邻两格中心之间的条带（3×40×160），每条候选边出一个 logit，温度校准 + sigmoid、阈值 0.5，判格子是否连通 |

四个都是**判别式小任务**，不是通用识别。注意 `operators_det` 认的是**血条**而不是立绘。

### 8.2 决定性的事实：仓库里没有任何训练链路

`tools/` 里只有截图、取色掩码、取坐标、模板去重这类**采集辅助**工具；没有 `.pth`、没有 `train*.py`、没有数据集与标注流程；`docs` 里搜 `onnx` 只命中 onnxruntime 依赖声明。**四个模型都是外部产出。**

唯一的闭环是**采数据**：`BattlefieldClassifier` 在"类别变化 / 分数 < 0.75 / 超过 10 秒"时**自动截图**到 `debug/skill_ready/{c,n,y}`，注释写明"为重新训练模型截图"，保留 50 张。

→ **所以门槛不是"用卷积还是特征匹配"，而是"带标注的数据从哪来"。** 而它给出的范式可以直接照搬，见 8.3 第 1 条。

### 8.3 对 A4 最有用的三条

1. **在"模型自己不确定"时自动采集样本。** 触发点是低置信度与状态切换，而不是固定时刻——等于让模型主动告诉你哪些样本最值得标注。这份数据同时是**训练数据、A4 基准集、回归输入**（已写入概念文档 5.5）。
2. **颜色/统计量可以当主判据，模板只负责定 ROI。** 它有 `pureColor` 开关，打开后**完全丢弃模板匹配分数**，只按颜色区间统计量判定；配置注释里明写"背景立绘变化""避开外圈动画""背景透光干扰，只取 250+ 纯白"。配合 `maskSrc`（掩码取自**原图**，语义是"排除遮挡物"）——**把遮挡区域从待匹配范围里挖掉，只匹配没被盖住的那部分**。它的冷却头像就是这么做的：只比对未被高亮盖住的暗部。这就是"特效包住干员"的现成答案（已写入概念文档 5.4）。
3. **前帧跳算 + 事务化。** 前帧跳算：同一 ROI 的上帧灰度 CCOEFF > 0.98 就判"这一帧没变"，直接沿用上帧结果、不跑 OCR——常速运行时大量帧是"什么都没变"的。事务化（BlackFlow）：propose → preview → commit（带 revision 校验）→ observe（核对落点）→ apply，任一步不符即中止。

   → **修正第七节之后的一个说法**：此前记的是"它没有动作是否生效的反馈闭环"。更准确的是——**它有，但只在 BlackFlow 里；常规战斗路径确实没有**（那条路上 `do_action` 的返回值被丢弃）。所以我们不是要发明它，而是**把它从 BlackFlow 搬到战斗路径上来**。

### 8.4 格子对齐：它不靠图像拟合，靠 3D 相机投影

战斗地图**不做图像对齐**：关卡数据给机位、欧拉角、fov，用 `world_to_screen` 把格子的世界坐标投影成像素；镜头平移靠累加 `camera_shift` 重算全部格子位置。

唯一做图像侧拟合的是 `GridReconstructor`：搜索格间距 92~108（步长 0.25）、用锚点反推原点、要求网格落在 ROI 内，带最多 20% 外点剔除的鲁棒平方和与向先验 101 的正则，并**输出 residual 供校验**。

→ 对我们的含义：**地形资产必须携带"格坐标 → 像素"的投影参数**，屏幕位置由投影算出，而不是每帧从画面里找格子（已写入概念文档 2.1）。`GridReconstructor` 可以当兜底：投影参数缺失或失准时用它反推，并**用 residual 做可信度上报**——这正好接上 5.4 的"零假事实"。

### 8.5 它没解决、我们必须自己解决的

1. **密集重叠的实例分离。** NMS 与 MultiMatcher 都是**合并压制**（交集大的只留最高分）——**它根本不打算数清重叠的敌人**。分水岭、关键点、多目标跟踪都要自建。
2. **时序一致性。** 全仓库没有多帧投票、没有轨迹关联、没有状态平滑；敌人的数量与位置**没有跨帧模型**（`EdgeDetector` 收了 frames 却只用 `frames.front()`）。
3. **训练与标注。** 四个模型外部产出，重叠/遮挡样本、合成遮挡增强要自造。
4. **被特效包住的语义。** 它只回答"这一格有没有东西"，不回答"泡泡下面是谁"。

**注意第 4 条对我们其实不构成障碍**：我方干员的身份另有第二来源——我们自己下达的部署记录。所以我们知道自己下了谁、下在哪；识别要补的是"它还在不在、状态如何"。

**而第 1、2 条反而是我们架构上的优势**：我们有**暂停、慢放、时间片存储**——同一个战局状态可以被反复观察（暂停时反复看、慢放下看 10 倍时间、跨轮次重复观察），**多帧投票与轨迹关联对我们比对 MAA 便宜得多**，因为它必须在单帧里一次性把答案定下来，而我们不必。

### 8.6 A4 判据的收敛

综合以上，A4 的判据可以再精确一层：

> **不是"能数清重叠的怪"，而是"数不清时明确说数不清"。**

MAA 的 NMS 只回答"这里有一个"，连"这里其实可能有三个"都不说。我们要把它升级成"**这里至少有 N 个、置信度 c**"，而**不是**升级成"精确数出三个"。这个区别直接决定 A4 的工程量。

## 九、补充回查：地形资产的字段与做法

**起因**：地形资产的规格要定稿，回查它那份逐关格数据的字段设计与消费方式。

**口径**：4256 份逐关文件、424174 个格子、**没有一行不等长**（全部铺成矩形，空白处用同一个填充类型盖住）。以下用我们自己的词汇描述，不采用它的字段名与 schema。

### 9.1 它有什么

每关：

| 它有的东西 | 说明 |
| --- | --- |
| **关卡键（四个并存）** | 内部关卡 id / 游戏内编号 / 所属活动路径 / 关名，**任意一个都能查到，为空的那个自动忽略**；其中"游戏内编号"**允许缺失** |
| **网格尺寸** | 宽、高**显式存**——虽然从数组就能推出来 |
| **投影** | **两个 3D 机位**（正面 / 侧面） |

每格五个字段：

| 它的字段 | 语义 | 对应我们的哪一样 |
| --- | --- | --- |
| 可部署性（**4 值**） | 谁都不能放 / 只能放近战 / 只能放远程 / **两者都能放** | ⚠️ 见 9.3 |
| 高度位（2 值） | **世界坐标的层**，不是"地面/高台"这种语义标签 | ⚠️ 见 9.2 |
| 起点旗标 | 敌人出生 | 地标 |
| 终点旗标 | 我方目标 | 地标 |
| 细分类型（**107 种**原始值） | 具体地形：路 / 墙 / 洞 / 深水 / 岩浆 / 传送门 / 草地 / 商店地板…… | **就是我们说的"标签"** |

### 9.2 会咬人的第一件事：高台在屏幕上有偏移

格子的世界高度是 **`高度位 × −0.4`**——也就是说**高台格子在屏幕上的位置比同格的地面高一点**。

如果我们把投影做成"纯二维仿射"（格坐标 → 像素，只吃行、列两个输入），**每一个高台的屏幕位置都会系统性偏掉**。而且偏得很小、看起来"差不多对"，属于最难被发现的那一类错。

→ **投影要吃三个输入：行、列、高度位。**

**实测它的量级**（304 关采样、1280×720，按它的投影公式代入）：

| 量 | 最小 | 中位 | 最大 |
| --- | --- | --- | --- |
| 高台偏移（px） | 14.7 | **18.9** | 35.3 |
| 偏移 ÷ 列间距 | 0.20 | **0.20** | 0.60 |
| 其中竖直分量（px） | 14.7 | 18.8 | 28.1 |

两条性质：

- **几乎是纯竖直的**（横向只有 2 px 量级）；
- 但它**不是常数**——格子尺寸跨关卡差近 2 倍（列间距 61–112 px、行间距 53–103 px），**同一关内因透视也在变**（列间距最大/最小中位 1.24，极端 6.7）。所以偏移是**位置相关**的，"存一个常数"这个说法不成立。

再往下算一步，**它真正咬人的地方只有一处**：偏移 ÷（半个行间距）中位 0.58、最大 2.33，**304 关里有 5 关超过 1**——那几关按名义中心点击会落到下面那一格。

**而识别路径可以完全绕开它**：干员身份来自我们自己的部署记录（不靠识别），血条与技力条靠**搜索**而不是靠钉死的格子 ROI，地面敌人不上高台、飞行敌人不吃高台偏移。所以这个量只跟「格 → 像素」这一个方向有关（部署点击），跟「像素 → 语义」无关。

**对点击 vs 对 ROI，结论不一样**：格子的菱形半高约是行间距的一半，所以中位偏移下"点名义中心"仍然落在本格里；但**ROI 往往只有几十像素**，19 px 的系统性偏移会让高台上的 ROI 稳定偏。

→ 因此建议：**不建模成"第三个投影输入"这种抽象，只在投影里加一个按高度查的常数**。成本是一个数，换掉一整类"高台总是偏一点"的疑难。

### 9.3 会咬人的第二件事："两者都能放"这一档我们表达不了

我们现在的模型是 `可部署（是/否）× 高度（地面/高台）`。它能推出"只能放近战"和"只能放远程"，但推不出**"近战远程都能放"**。

而它那一档有真实用量，落在深水、足球场、气球、某种商店地板这类地块上（需要借助特殊道具才能部署的那些）。

→ 可选改法：把"可部署"从布尔改成「**谁能放**」——只能近战 / 只能远程 / 都行 / 都不能。这样部署判定直接从字段读、不用推导，也不会丢档。

**当前结论：暂不采用。** 合约里至今没出现过这类格子，所以保持「可部署 × 高度」两轴，**遇到再补一档**。

### 9.4 值得直接借的四个做法

| 做法 | 为什么好 |
| --- | --- |
| **总索引 + 逐关文件两级** | 一份约 1.4 MB 的索引（关卡键 → 文件名 / 尺寸），运行时先查索引、再按需打开单关文件。逐关文件便于人工维护与 diff，索引负责查找 |
| **未知类型降级 + 告警** | 107 种原始类型映射到 19 个语义键；映射表里没有的**降级成"无效"并打警告**，不崩、不猜。与我们"识别失败必须降级、不得消失"是同一条纪律 |
| **门用独立旗标** | 起点旗标出现在**三种不同外观**的格子上（专用起点格、路、地板）。外观与角色解耦，正是我们"地标是独立属性"的做法 |
| **同一套投影也用来定位 UI 按钮** | 撤退 / 技能按钮的位置写成世界坐标里的相对值，用**同一套投影**算屏幕位置，所以地图缩放平移时按钮跟着走。我们只想到定位格子，这条提醒我们**按钮也挂在同一套几何上** |

### 9.5 一处修正（针对 §8.4）

§8.4 写的是"关卡数据给机位、欧拉角、fov"。**更准确的是：关卡数据只给两个机位**；**欧拉角、视场角、分辨率都是代码里写死的常量**。结论（投影参数要进资产）不受影响，但读者会误以为这些都是每关不同的。

### 9.6 它做了而我们不需要的

**侧面机位与"多战场"判定。** 它为每关算两套屏幕坐标（正面 / 侧面），并在"起点或终点被投到画面外（带 5% 容差）"时把这一关标记为**有多个战场**（地图会横向滚动）。我们明确只做单屏，所以不需要。

但它的处理方式有个提醒：**"几何对不上"不一定是数据错，也可能是关卡特例。** 我们原本打算"投影对不上就拒绝执行"，得留一条——这类情形要能**被显式建模**，而不是一律当成错误。

### 9.7 它存了两套机位，第二套就是慢放视图

它的每关数据带**两个 3D 机位**。查它的消费方可以确认第二套用在哪：**把干员卡拖到指定格**那条路径里，算拖动距离用的是**第二套**的格子屏幕坐标。

也就是说：

- **第二套机位 = 慢放（拖动 / 选中干员）时的视图**；
- 两套的差别是**欧拉角倾斜 10°**（常态 0°、另一套 10°）**加机位平移**——正是"开慢放后地图往右倾斜并位移"。

另外，它的投影函数**留了一个相机平移量参数**（`calc_tiles_info` 带 `shift_x/shift_y`），平移后**重算全部格子的屏幕位置**；我们看到的调用点大多传 0，但能力在那儿。

→ 对我们的含义：**投影不是静态的，也不止一套。** 地形资产必须能提供**常态与慢放两套参数**，切换时间态时同步切换。慢放下的部署点击、以及关键时段的识别 ROI，**都必须用慢放那一套**。已写入 [地形模型](../30-专题/地形模型.md) §10。

这同时给 §9.6 那句提醒补了一个具体例子：**"几何对不上"可能只是因为视图切换了**——不是数据错，也不是关卡特例，而是我们自己忘了切投影。

## 十、补充回查：它怎么处理干员与敌人的状态

**结论先行：它不建模。** 全仓库不存在 buff / debuff / 状态的数据模型。它靠"5 个标量条件 + 线性动作时间轴"绕开，语义完全由作业作者承担。

这一节的用途是**划边界**：效果识别这件事在它那里**没有先例可抄**，"新增一层设计"是必然的。

### 10.1 没有状态模型

- 全仓库唯一的 `buff` 标识符是保全派驻导能元件的**名字字符串**，当 OCR 文本用，与状态无关。
- 干员静态模型只有 id / 名字 / 职业 / 子职业 / 攻击范围 / 星级 / 排序 / 位置类型；数据文件里检索 `skills|talents|buff|abnormal|effect|status` **零命中**。
- `AbnormalStatus` / `StatusEffect` / `BuffType` **零命中**。
- 沉默 / 晕眩 / 冻结 / 浮空 / 沉睡 / 战栗 / 恐惧 / 麻痹 / 诱导 / 束缚 / 庇护这些词，全仓库只出现在肉鸽收藏品的展示文本、关卡名、干员名、翻译表里，**没有任何 C++ 读它们**。

### 10.2 它的绕开方式

作业 JSON 的条件**只有 5 个整数**，且是与的关系：击杀数 / 费用绝对值 / 费用变化量 / 待部署区处于冷却的干员**个数** / 全局计时器毫秒。schema 自己挂着 `// TODO: 其他条件`，且、或两种条件的组合方式也未实现。

决策逻辑用到的量只有：上面那 5 个、待部署区干员表、场上干员坐标表、已占格表、技能记账、静态地图。**没有一项涉及敌人，或涉及效果。**

取向值得注意：**条件刻意选在全局单调、且天然对齐时间轴的量上**（费用与击杀数只往一个方向走）。效果类状态恰恰相反——非单调、局部、易反复。**这是它回避的原因，也正是我们卡住的根因。**

### 10.3 它的识别清单：一个敌人都不认

识别的是：部署费用、击杀数 / 总数、保护点 HP 图标（**只判断漏没漏，不读数值**）、是否处于战斗界面、待部署区每位干员的头像 / 职业 / 费用 / 可用 / 冷却、技能是否就绪（3 分类）、部署朝向（4 分类）。

三条硬事实：

- **没有任何一处识别状态或效果**；
- 视觉层代码里检索"敌人"**零命中**，模板目录下**没有敌人模板、也没有效果图标模板**；
- 唯一"看到干员在场上"的检测器（血条）**不在实时战斗循环里**，只被实验性的"录像转作业"调用。

它**全程不读技力 / SP**，只有一个"技能就绪 / 未就绪"的三分类。

### 10.4 它的动作账本里没有"目标敌人"

动作类型共 15 种，但**每个动作的作用对象永远是我方**（干员名 / 职业 / 格子三选）。**结构里根本没有"打给谁"这个字段**，所以"技能放给了哪些敌人"在它那里既没记录、也无从推算。连那个从录像反推操作的实验功能，也只反推出部署 / 撤退 / 开技能三类——**同样不读效果、不记目标**。

→ **对我们的含义**：二档推算要成立，动作上必须挂一条「**预期后果**」。它已经有归宿（概念 §2.2 第 14 条「每个动作都必须有可观测的生效反馈」+ 时序层 §4），归**记录**，不进轴。
→ 它还需要两样输入：干员的**攻击范围**（数据库）与**当帧敌人位置**。所以「数据库要给攻击范围」从锦上添花变成**必需**。

### 10.5 值得借的

| 借什么 | 为什么 |
| --- | --- |
| **结算界面的检查锚点** | 它有一处"是否仍处于战斗界面"的检测，锚点是**暂停按钮 / 击杀图标 / 费用左侧图标**；模板目录里另有一个结算类目录。正好能填我们那个"待补：两类结算画面的截图" |
| **生效反馈的重试 / 放弃参数** | 点完技能**立即复检**，失败累计 **3 次**就永久放弃对该干员用技能，并计入错误计数。我们只有"动作必须带生效反馈"一句原则，这是现成量级 |
| **地形数据结构的印证** | 它的格子是「可部署 + 高度 + 类型键 + 坐标」，与我们地形模型的两个正交属性对得上 |
| **就绪判定 ROI 的取舍证据** | 它的就绪 ROI 锚在**格子的像素坐标**上（钉死投影）——正好印证视觉层 §3 记下的那条差异：我们改成"在邻域搜索"，不要求坐标准 |

### 10.6 一处别误读

**那 5 个条件不是"经过论证的最小集"**——schema 自己写着 `// TODO: 其他条件`。它只是"发到了这里"。

### 10.7 结论：它是绕过，不是解决

它的成本压在全**局单调标量**上，我们把同样的钱花在敌人与状态上。**所以"剩下那部分"只能自己设计。**

有一条它无意中给出的独立验证：它判断干员是否离场，靠的**也是待部署区**（可用性 + 冷却），不是场上血条——与视觉层 §5 选备战席卡片是同一条路，而且是各自独立得出的。**"能用肯定证据就别用否定证据"这条站得住。**

另外它**没有任何技能 CD 时长模型、也没有持续时间模型**。所以"要新增一层"不只包含效果识别，**也包含时间模型**（我们的「时效」字段）。
