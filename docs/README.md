# docs 目录说明

> 状态：已定 ｜ 改这套结构以前，先改这份文件

这是本项目的设计文档树。

## 1. 为什么要这么分

设计文档里混着两种寿命完全不同的东西：

- **定了、以后不该再动**的结论（责任边界、时间三态、地基约束）；
- **还在吵、随时翻盘**的（视觉层怎么做、工具集长什么样）。

混在一个文件里的后果：每讨论一次就改一次，定死的结论被埋在中间，过两周谁也说不清哪句还算数。

所以这棵树**第一层按"寿命"分，第二层才按话题分**。

## 3. 内容该写哪

依次问：

1. **"系统现在长这样"？** → `10-规格/`
2. **"我们做了一个选择，以后不该反复改"？** → `20-决策记录/` 里对应子系统那份日志
3. **"还没定、有几个选项在争"？** → `40-讨论稿/`
4. **"约束所有子系统"的模型或标准？** → `30-专题/`

规格和专题的区别：**规格是将来会变成代码模块的东西；专题是跨模块的约束。** 比如"暂停和慢放怎么实现"是规格，"一帧是多少毫秒、时间怎么计量"是专题。

**一个结论只有一处写正文。** 别的地方要提它，只放链接；为了让读者读得懂，允许带一句**非规范性复述**——但条件、阈值、边界、取值这类规范内容一律不复制。

判定标准很硬：**改这条结论要动几个文件？超过一个就是双写。**

**定义处还不存在时，写占位引用，不要自己填一份：**

> 此处需要 X ｜ 由《哪份文件》定 ｜ 本文件不预设形态

占位不是偷懒。没有它，需要这个东西的每一处都会各自填一遍，同一个洞被填两次、两次还不一样，**而两份看起来都像结论**。

## 4. 文件头部状态行

每个文件第一行用一个引用块写状态：

> 状态：未开始

五种取值：`未开始` / `讨论中` / `已定` / `已取代` / `已归档`。
`取代`、`被取代` 两个字段只用在决策条目上。

## 5. 拆分阈值

任何一份文件，满足**任一**条件就拆：

- 超过约 200 行；
- 里面出现了两簇互不依赖的内容。

拆法：`某主题.md` → `某主题/` 目录，里面 `README.md` 留概览，其余按主题分文件。

这条是整套结构"避免单文件膨胀"的真正机制——不靠自觉，靠一条能判定的阈值。

## 6. 讨论稿怎么用

`40-讨论稿/` 是真正干活的地方。文件名就用话题名。

一个话题定案以后：

1. 结论写进 `10-规格/`，或者作为一条决策记进 `20-决策记录/`；
2. 决策日志里写 3–5 行「考虑过的其他方案」，把否掉的理由留下来；
3. 原讨论稿移进 `90-归档/`，**不删**——三个月后你会需要它来回答"当初为什么不那样"。
