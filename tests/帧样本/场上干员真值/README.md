# 帧样本 / 场上干员真值

**面板开着的那 13 帧** —— 一帧里同时有**真值**（面板上那一行 `生命 当前/上限`）与
**被读的那根条**。它是[场上干员那三条读数链](../场上干员/README.md)的**独立判据**。

## 为什么要另开一批

`HP_COLOUR_TOL` / `GAP_TOLERANCE` / `SKILL_FILL_TOL` / `DIAMOND_SOLID_SCORE` 这些常量
**都是拿第一批**（`../场上干员/`）**量出来的** —— 按[基准集](../../../docs/10-规格/采集与验收/基准集.md)
§4，那一批**不再干净**。这一批是**另一批**：链的参数**没有一个是拿它的数字定的**。

## 硬纪律：**不许拿面板上的数字去调链**

面板上的数字是**真值**，只进「对照」那一步：链先把 13 帧读完、写进 `frames`，**之后**才把
真值读进来做减法 —— `scripts/bench_field.py` 里 `_truth_rows()` 那一圈**看不见**真值，
真值只出现在 `TRUTH_PICKS` 那一个表里。

**这一版链改过一次，但不是拿它改的**：技力那一侧的填充判据（`SKILL_FILL_TOL`）与
`GREEN_MAX_RG` 是拿 `data/probe/sp_series` 那五帧（亮底上整条判成填满）定的 ——
**这一批的 13 帧一帧都没参与**。这一批的读数在那之后**重跑了一遍**，所以它现在对
「**这一次**改动」来说已经不是「没见过」的了；**下一轮再改链必须换一批**（[基准集] §4）。

## 这一批拿掉了哪一帧（按裁定）

原来是 14 帧。拿掉的那一帧是**备战席干员的详情页**（点的是备战席卡片，不是场上干员）——
它**不属于本批的取帧场景**：本批的配对规则（「被选中的那根条 = 离画布中心最近的那根」）
只在**点场上干员开面板**时成立（那时被点中的干员会被挪到屏幕较中心的位置），而**点备战席是
另一回事** —— 整个场景朝固定的右上方挪，与被点的卡在哪无关。所以那一帧不是「配对可疑」，
是**这条规则管不到它**，于是**整个拿掉**：留着会让人以为配对只是可疑。

拿掉之后**剩下 13 帧全是点场上干员开的**，这一批干净。

旁边还有两批：[场上干员](../场上干员/README.md)（判据的量尺来源，不再干净）与
[场上干员回归](../场上干员回归/README.md)（亮底那五帧的**回归批**，不是干净基线）。

## 配哪一根条

点场上干员开面板时，**被点中的那个干员会被挪到屏幕较中心的位置**（场景跟着一起挪），
所以**被选中的那根条 = 离画布中心最近的那根**（画布中心 = `(1400, 630)`）。

`取材.json` 里每一帧都记着**这一根的距离**、**第二名的距离**与**全部候选** —— 挑错了
看得见。这一批**不是**靠「面板上是哪个干员」去配的，靠的是这条几何规则。

这一批**全是「点场上干员开面板」那一档**（另一档——点备战席——那一帧已按上面的说明拿掉）。

技力那一侧（真值 = 场上那个技能按钮上的 `N/M`）：**只有 `sp_now` 一帧有**，
`16/26 = 0.615385`，而链读到 `93/146 = 0.636986`（**精确值**，含义 充能中）→ 误差
**+0.021601（+3.154 px）**。

**这 +3.15 px 不是链多读了列**：那一帧的绿条**自左起实绿 93 列**（`93/146 = 0.637`），
链读的 93 列**就是那 93 列**；差出来的那 3.15 px 是**面板上的 `16/26` 与条上那 93 列之间
的差**（`16/26 × 146 = 89.85`）。换句话说：对着**条上的像素**是 0 列误差，对着
**面板那个分数**是 3.15 列。这一批两边的数都列出来，谁都能自己算。

## 误差分布

**全部 13 帧**：中位 **+0.002256**、两端 **−0.001333 … +0.005162**、最大绝对 **0.005162**、
**双边**（有高有低）。以像素说：中位 **+0.329 px**、两端 **−0.195 … +0.754 px**。

技力那一侧只有 1 帧，所以它没有「分布」，只有那一个数：**+0.021601**（单边，读高）。

两列都在 `判据读数.json` 的 `health_errors` 与 `sp_errors` 里。

## 这一批**看出来的东西**（只报，不改）

1. **血条**：13 帧的误差全在 **±0.0052**（±0.75 px）以内，方向**两边都有** —— 没有系统性偏一头。
2. **技力那一侧上一版读高 25 px，这一版读到 93 列 = 实绿那 93 列。** 改的是**判据**，不是参数：
   旧判据是「逐列中位亮度 ≥ 这一条自己中位亮度 × 0.55」，它把绿条右边那 22 列（亮度掉到
   中位的 0.587 倍、边界半亮）算成了填着 → 读到 `115/146 = 0.788`（区间 `0.788–0.836`）；
   新判据量的是「这一列的颜色离**这一条自己的填充色**多远」，那 22 列不是填充色 → 不算填着。
   （这一段是**拿 `data/probe/sp_series` 那五帧定的**，见 `field.SKILL_FILL_TOL`；
   这一批只提供改动**之后**的读数，它没有参与定参。）
3. **同一个原因把含义也修好了**：这一帧那条绿条的 `R − G = −3`，原来落在
   `GREEN_MAX_RG = −8` 与 `ORANGE_MIN_RG = 40` 之间 → 含义读成**认不出**；而它其实是
   **充能中**。那一格原来的文档写着「绿条那一簇是 −36 … −1」，与实测对不上（绿条不止到 −1）——
   现在 `GREEN_MAX_RG = 0`，这一帧的含义从「认不出」变成「充能中」。

## 没覆盖到什么

- **只有一种真值来源** —— 面板那一行 + `sp_now` 那个技能按钮，没有第二种独立来源去交叉核；
- **技力那一侧只有 1 帧**（另外 12 帧上那个按钮根本没画出来），所以技力误差的样本量是 1；
- **没有接近 0 的极值** —— 最低那一档真值是 `0.183`；
- **没有暂停态、没有退场动画、没有永续技能** —— 全是常速帧；
- **空轨道单独可见 / 极低填充 / 血条被切断** 三档这一批也一帧都没有（与第一批同一个缺口）；
  那两档**认合成用例**、不必再去找（裁定）—— 钉在 `tests/unit/test_vision_field.py` 里。

## 怎么重跑

    .venv\Scripts\python.exe scripts\bench_field.py

它把这一批与第一批**一起**建、一起落读数。**跑两次，两份报告都逐字节一样**
（没有时间戳、没有绝对路径、没有随机量）。

## 这一层不判断「够不够」

逐帧误差、分布、两端、单边还是双边，都在 `判据读数.json` 里；**「够不够」是规划者的事**。
