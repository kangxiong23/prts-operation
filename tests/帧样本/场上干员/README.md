# 帧样本 / 场上干员

**「场上那个我方干员现在什么样」那一格的测试夹具** —— 血条 · 技力条 · 可释放菱形，
一帧一块，每块比**取区**大一圈。

## 这是什么，从哪来

从**原生帧**裁。三条链各自要读的东西画在同一条横带上，所以一块裁剪装得下三样：

| 文件 | 内容 |
| --- | --- |
| `NNNN.png` | 16 块 `300×420` 的原生像素裁剪（一个都不缩） |
| `index.json` | 每块的原点、尺寸、源帧路径与**源帧 sha256**（钉住「这块出自哪一帧」） |
| `取材.json` | 每块用的是**哪一个取区**、它从哪个血条左上角折出来、这一块补的是什么 |
| `判据读数.json` | 三条链逐帧的读数、两簇的分布与空档、覆盖说明、**整批 16 条各自的**锚点摆动 |
| `菱形模板.png` | **黄**那个图标模板的样子（给人过一眼用的）；**灰**那个的模板在 `assets/features/close_diamond/` |

源帧是 `data/precheck/cd/`（一局真机战斗每 3 秒一张）· `data/precheck/live/`
（探索期扫的 40 帧）· `data/probe/_t5_board/` 与 `_t5_field/`（T5 那两次原生抓帧）。
那几批全帧是 gitignored 的临时产物，所以把**要用的那一块**搬进版本库，让验收能反复跑。

**有损 JPG 一张都没用**：`tests/示例图片/` 里那几张演示图是 1920×864 的 JPG，与原生
2800×1260 差一个尺度、又压过一次，`scripts/bench_field.py` 直接拒绝这类源。

## 取区是什么形状，裁剪为什么比它大

三条链共用**一个取区**（`240×360`）：

- **血条左上角**落在取区里的 `(40, 320)`；
- **技力条**紧贴血条下面那一行；
- **黄菱形**的中心落在 `(112, 87)` —— 也就是血条左上角 **+(72, −233)** 处。

裁剪取 `300×420`（原点 = 血条左上角 − (80, 340) 上下），**比取区大一圈**。
理由与[基准集](../../../docs/10-规格/采集与验收/基准集.md) §3 那条同源：把 ROI 预先替
识别链做好，测的就不是同一条路了。这里被测的那一段是「**窗里的哪一块是条**」。

**取区本身是参数，链不产生它**：干员在屏幕上的位置来自部署记录 + 投影
（[状态层/我方干员](../../../docs/10-规格/状态层/我方干员.md) §位置），而那个「在哪」
不在这一单里。所以三条链把取区收成一个 `PixelRect`，`operator_ui_window`
只负责「血条那块矩形 → 取区」这一次折叠。

## 覆盖到了什么

**血条**：八档不同的填充 —— 满（多帧）· `0.993 · 0.884 · 0.829 · 0.781 · 0.740 · 0.301 · 0.288`。
降级两支都出现过：**精确**（15 条）与**下界**（`shot04_a`：填着的那一截被**别的条**压过）。

**技力条**：含义三档齐全（绿 = 充能中 · 橙实心 = 生效中 · 橙带竖线 = 弹药分格）。
填充有满（12 条）、有 `0.863`（`shot21_a`）· `0.808`（`shot01_a`）· `0.527`（`shot31_a`），
有**下界** `0.808`（`shot26_a`：弹药没填满）。
**技力那个字段**在生效中 / 弹药分格那 4 条上落**未采样**。
（`sp_of` 那条「下界 → 加宽成区间」的支路，**这一批里现在一帧都不触发** ——
原来触发它的那一帧是坏样本，已删，见下。）

**黄菱形（可释放）**：在 8 条（分数 `0.543–0.895`）· 不在 8 条（分数 `0.129–0.279`），
批内空档 `0.279–0.543`。

**条被挡住的那一档**：`shot04_a`（条上压着**别的条** → 缝 **8 列以内**，
用另一条缝宽容度 `COVER_GAP_TOLERANCE = 10` **跨过去接着算**，跨过去之后最后一列还是填充色 →
仍读**满条**）· `shot30` / `shot22`（条**右边那一截背景比条本身还亮**，实测条 145–157、背景 164–213）。

**图层事实（用户给的）**：**特效与干员贴图都在血条 / 技力条下面**，能挡住条的只有
**别的条**（比如怪的）与**黄色菱形**。所以「条被特效染了色」这种事**不存在**；
读到一根颜色对不上的条，多半是**取区里不止一根条**（格里有好几根、或者条只截了一部分）——
那种帧按用户对「很难判准」那一档的要求，应当报**未采样**。

**锚点摆动（铺到整批 16 条）**：**每一条各自**沿 x / y 挪 ±1 / ±4 / ±12 px，判据是三条链的
结论（形态 / 含义 / 菱形那个布尔）一字不变、且血条那个比例挪动不超过两步。结果**不是
「一条都不翻」**：

| 哪一条 | 哪一轴 | 挪多少 | 翻成什么 |
| --- | --- | --- | --- |
| `shot02_a` | y | −4 / −12 | 技力填充 **精确 → 下界** |
| `shot04_a` | y | +4 / +12 | 技力填充 **精确 → 下界**（那条缝跨不过去了） |
| `shot26_a` | y | −4 / −12 | 含义 **弹药分格 → 充能中** |

其余 **16/16（x）与 13/16（y）**在 ±12 以内一字不变；再往外挪（±16 起）**每一条**都翻
（那是整格错位，窗口已经开在别的干员上了）。逐条读数在 `判据读数.json` 的
`sensitivity.crops`（汇总在 `sensitivity.summary`，翻面明细在 `coverage.swing_within_tolerance`）。

**上一轮这一条只报了 `cd01_a` 一条**，写成"±12 px 结论一字不变"—— 那是**拿一条帧的读数
代替整批**；铺开之后就不成立了。这一版把 16 条全铺开，并如实列出翻面的那 3 条帧。

**换判据之后翻面的条变过两次**：技力填充那一把尺子从"亮度"换成
"颜色"、又被压住那一档的缝宽容度（`COVER_GAP_TOLERANCE`）改了一次 —— 同一根条在同一个位移下
能不能翻，跟着一起变。窗口该多宽是**规格问题**：这里只把读数报出来，不去替它定。

## 没覆盖到什么

- **极低填充**：低于约 3% 的血条一帧都没有 —— `MIN_FILL_COLUMNS` 那一档只有合成用例；
- **血条被切断**：填着的那一截中间被压断、缝两边都还亮着的真帧，一帧都没有 ——
  只有合成用例（单元测试里拿真帧抹掉中间几列造的那一支）；
- **边界渐变 -> 区间**：真帧上没有「填着的那一截右边半亮」的那一档，两支区间只有合成用例；
- **技力条填充的区间那一支**：真帧上**一帧都没有** —— 「半填」那条带子只有
  `SKILL_FILL_TOL`（48）到 `_SKILL_HALF_LIT_CEILING`（56）那么窄，而实测的边界是
  **一步跳过去**的（填着那一侧最多 40，紧接着那一列就跳到 **68 / 87 / 88 / 93 / 94 / 106 / 149**），
  所以真帧上这一支**不触发**；它靠合成用例钉（裁定：**合成用例不许删** —— 真帧不触发是
  取舍，不是这一支可以死）。
  （**这条带子为什么取这么窄**：先试过 48 的两倍（96）—— 那会把 68/87/88/93 误判成
  「半填」，本该精确的读数被摊成区间 —— 带子只能取在 40 与 68 中间那一段。这是一个取舍。）
- **取区里不止一根条**（格里有好几根条、或者条只截了一部分）：这一批里**一帧都没有** ——
  取区本来就该由调用方给对；给错了会读出一个**没有意义**的比例。按用户对「很难判准」那一档的
  要求，那种帧应当报**未采样**。（**这一批原来有一帧是这一档，已经删掉**：它被用户判为坏样本 ——
  那一格里有好几根条、还都只截了一部分。删除的理由不是"读数不好看"，是**它读到的不是一根条**，
  拿它当判据会把判据本身带偏。）
- **被压住那一档的缝宽容度只有一条帧撑**：`COVER_GAP_TOLERANCE = 10` 的上沿是拿 `shot04_a`
  那条缝（最宽 8 列）定的，下沿是拿 `sp_series/s02` 那条轨道（最窄 19 列）定的 ——
  **两头都各只有一帧**。缝在 9…18 列之间的"被压住"真帧，这一批里**一帧都没有**。
- **技力含义的「认不出」那一档**：**这三批**（16 + 13 + 5 = 34 帧）里一条都没有 ——
  `meanings` 里一个 `unknown` 都没有。那一档**仍然留在判据里**（颜色对不上任何一族就落它，
  那是一条**语义**判断，不是"没见过就不要"）。**真帧在难例批** —— 逐块落法见
  `../场上干员难例/判据读数.json` 的 `coverage`（**覆盖文本的正文只在那一处**，
  这里只引用、不重抄）；
- **空轨道单独可见**（血条接近空、能看清暗轨道）：这三批里一帧都没有 —— 真帧在**难例批**；
  **「条在、只是空了」与「条不在」是分得开的**（空的条留下一条条形变暗区 → 条内比条外暗，
  判据 `field._looks_like_an_empty_track`）；极低填充仍然落未采样，但那是**另一条线**
  （填充连段短于 `MIN_FILL_COLUMNS`），不是「分不开」（同上）；
- **技力条掉到零**（一条全暗的技力条）：这三批里一帧都没有 —— 难例批那一块是「空轨道被背景
  染了色」，不是「一条全暗的条」（同上）；
- **暂停态下的菱形**：全是常速帧，菱形在暂停态下自己在动那件事没测；
- **永续技能**：这一批没有永续技能的帧 —— 读得出「生效中」，而「没有还剩多久」由数据库那侧决定；
- **同一根条随时间的连续变化**：`cd` 那批是连续的，但这里只挑了四帧，
  没有把整段充电过程铺开。

**卡在哪一条**：「极低填充」与「血条被切断」两档在现有原生帧里**一帧都找不到** ——
**不必再去别处找了**（裁定）：**认合成用例**，这两档在 `tests/unit/test_vision_field.py` 里
用合成帧钉着（「被切断」那一支是拿真帧抹掉中间几列造出来的），并如实标注在
`判据读数.json` 的 `coverage.not_covered` 与 `stuck` 两处。**没有拿别的东西凑**。

## 这批东西的四条口径（[像素匹配诊断](../../../docs/30-专题/像素匹配诊断.md) §5）

- **哪把尺子**：
  - 血条：逐列**中位颜色**离 `HP_BLUE (110,190,228)` 的逐通道最大差 ≤ `HP_COLOUR_TOL = 24`；
    填着的那一截 = 自左缘起连续亮列（容 `GAP_TOLERANCE = 4` 列）；
  - 技力条：逐列中位颜色离**这一条自己的填充色**的逐通道最大差 ≤ `SKILL_FILL_TOL = 48`
    （填充色 = 自左缘起跳过 2 列、取 8 列的中位颜色）；填着的那一截 = 自左缘起的连续同色列
    （容 `GAP_TOLERANCE = 4` 列）；
    含义按**填着那一截**的逐列中位 `(R−G)`：≤ 0 绿 / ≥ 40 橙 / **正的那一段**认不出；
  - 菱形：`cv2.matchTemplate(TM_CCOEFF_NORMED)`，RGB 三通道，模板 `64×64`，
    在取区里 **±60 px 的邻域**上滑（不是钉在小框里）。
- **哪个取区**：`240×360` = 86 400 px；里面血条 `146×8` = 1 168 px；
- **取区原点从哪来**：常量网格 —— 取区左上角 = 血条左上角 − `BARS_IN_WINDOW`；
  血条左上角由调用方从部署记录 + 投影给出（**这一层不产生它**）；
- **去重按什么键**：**帧名**（批内唯一）。同一个源帧里两根不同的条各算一条
  （`cd01` 出了三条），所以去重按「哪一根条」而不是「哪一帧」。

## 它同时是一批基准集

按[基准集](../../../docs/10-规格/采集与验收/基准集.md) 的格式，`index.json` 是**第 1 版**。
加载它走 `ark.offline.bench.batch.load_batch` —— **全程不用真机**。
它**没有 `facts`**：抓这批帧的时候没记前提头。

## 菱形模板从哪来

从 `data/probe/rawcol_1.bin` 裁一次（`(1817, 211)` 起 `64×64`），落在
`assets/features/ready_diamond/diamond.npz`。那一帧**不在这一批里** ——
《视觉层/识别方法》§已定 那条纪律：图标模板**不许取自验收批的帧**。

**这是个人工框一次的地方**（[资产生成器/特征库](../../../docs/10-规格/资产生成器/特征库.md) §3
「图标模板」那一行），所以 `菱形模板.png` 留在这一批里给人过一眼；模板换一张，
这一批的读数要重跑。

## 这一批**不再干净**（独立判据是另一批）

`HP_COLOUR_TOL` / `GAP_TOLERANCE` / `SKILL_FILL_TOL` / `DIAMOND_SOLID_SCORE` 这些常量
**都是拿这一批量出来的**，所以按[基准集](../../../docs/10-规格/采集与验收/基准集.md) §4，
这一批**不能同时当独立判据**。独立的那一批是 [场上干员真值](../场上干员真值/README.md)：
13 帧、详情面板开着、逐帧拿面板那一行的 `生命 当前/上限` 当对照。
**面板上的数字一条都没有回头改过链**（那是它的硬纪律）。

**技力填充那一把尺子、`GREEN_MAX_RG` 与被压住那一档的缝宽容度不是从这三批定的** —— 是从
`data/probe/sp_series` 那五帧（亮底上整条判成填满）定的。那五帧现在**已经收进版本库**，
落成 [场上干员回归](../场上干员回归/README.md)（**回归批**，不是干净基线：它见过）。
这一批与真值那一批的读数都是在**改完之后**重跑的，所以它们对"下一次"改动才重新算"没见过"。

**三批的分工**：这一批 = 判据的**量尺来源**（不再干净）；[场上干员真值](../场上干员真值/README.md)
= **独立判据**（面板真值，13 帧）；[场上干员回归](../场上干员回归/README.md) = **防回退**
（亮底那五帧，读数钉在单元测试里）。

## 怎么重跑

    .venv\Scripts\python.exe scripts\bench_field.py

它跑三条线：**这一批**（建批 + 落 `判据读数.json` + 落模板）、
[真值那一批](../场上干员真值/README.md)（建批 + 落它自己的 `判据读数.json`）与
[回归那一批](../场上干员回归/README.md)（只落裁剪与清单 —— 它**没有**读数文件，读数钉在单元测试里）。
**前两条线各自跑两次，那两份报告都逐字节一样**（没有时间戳、没有绝对路径、没有随机量）。

## 这一层不判断「够不够」

读数、两簇、空档、覆盖，都在 `判据读数.json` 里；**「够不够」是规划者的事**
（那一格的规格网在夹具落地之后写）。
