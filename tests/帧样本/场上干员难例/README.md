# 帧样本 / 场上干员难例

**「场上那个我方干员现在什么样」那一格的补测夹具** —— 专挑**一格里有好几根条**、
**条与条挨得近**、**被黄菱形压住**的帧。它和 `../场上干员/` 是同一套尺寸与同一个
`index.json` 形状，但**它不是基准集、也不是真值批**。

## 为什么要补这一批

上一轮的问题有一部分是**样例太少**：老那两批里，一格里只有一根条的情形占绝大多数，
所以「邻条进窗」「条挨着」「菱形压在条上」这几档**几乎没有真帧压过**。

源帧是 `screenshots/run-01/` 那 12 张（用户 2026-10-07 那一段连拍里挑的，
整段 58 帧、10 秒一张，见同目录的 `manifest.csv`）。**原生 2800×1260，没有损 JPG。**

## 用户贴在文件名上的标签

| 帧 | 标签 |
| --- | --- |
| `hard_多个技能条紧挨着.png` | 多个技能条紧挨着 |
| `hard_多个技能条错位挨着.png` | 多个技能条错位挨着 |
| `special_带弹药机制的有竖线间隔的橙色技能条.png` | 带弹药机制的有竖线间隔的橙色技能条 |
| `special_黄色菱形挡住了技能条，很难判准，应报未采样.png` | 黄色菱形挡住了技能条，很难判准，**应报未采样** |

最后那一条是**期望输出**（用户写的），另外三条是描述。标签原文逐帧抄进 `取材.json`
的 `label` 里。

## 被测对象是怎么挑的：**候选查找器的全部输出，一个不筛**

每一帧跑一次 `scripts/bench_field.py` 的 `_bar_candidates()`（执行者写的**建批侧**
候选查找器），它给出几根就裁几块：12 帧一共 **52 块**。裁剪尺寸、取区折法与
`../场上干员/` 一模一样（`300×420`、血条左上角落 `(40, 320)`）。

**故意不筛。** 这一批要压的就是「窗里不止一根条」；一筛就把要压的那一档筛掉了。
代价是 `取材.json` 里的 `bar` 是**候选坐标**，不是真值坐标 —— 所以：

- 同一根条可能被记成**两个候选**（被背景切成两段），两条裁剪各是一块合法的窗；
- 挨着的那两条会**连成一段**，查找器可能给出一个 `lit` 比条宽还大的候选
  （`candidate_lit` 那一列）。**它不许当填充读数** —— 裁剪只用 `(x, y)`。

## 这一批量出来的一条几何事实：**紧挨着时，两条的重叠**

**条宽 146，而这一批里相邻两条的左缘只差 138** —— 也就是相邻两条会**重叠 8 列**。
用户给的画面事实：重叠那几列的底色会**加深**；**血条那一条上看不出加深**（看不出本条的
填充是在哪儿断的），而**技力条上的加深看得出来**。同一行上：

```
[1189 ... 1335)  第一条的轨道（146 宽）
            [1327 ... 1473)  第二条的轨道（左缘差 138）
```

于是「一条到底满没满」在**血条那一行上是判不出来的**：满条（146）与 0.938 的条
（137）在血条那一行上都只看得见一段蓝加一道接缝。要判，只能看**同一根条的技力条** ——
技力条没满，它露在外面的轨道到哪儿结束，那一帧的条就有多宽。实测：那一帧第二条的
技力填充是 118 列，链读 119 列，与「轨道 146」自洽。

用户还给了另一条：**进慢放状态会把「紧挨」变成「错位紧挨」**（见 `hard_多个技能条错位挨着.png`），
错位之后这一档是可识别的。

## 判据：另一条算法给的旁证

链走的是「一带 8 行取逐列中位色 → 找左缘 → 自左缘起连续亮列」。旁证换成**另一条路**：
取条中间那一行，自候选左缘起**逐像素**数下去，遇到第一个不像血条蓝的就停（不许有断口、
不取中位、不在 `±COL_TOL` 里搜）。两条路**共用颜色口径**（`HP_BLUE` / `HP_COLOUR_TOL`），
算法不同。

**它不是真值，只是旁证。** 这一批**没有落真值**（面板上的 生命 当前/上限），所以判得出
「两条路同不同」，判不出「链读得对不对」。

**这条旁证有一处已知的错**：它遇到第一个不是血条蓝的列就停，所以**会停在上面那道加深的
接缝上**，把满条数成 136 / 137 列；链跨过接缝报 146（满）—— 这一处是**旁证错、链对**。
读数里 `tight_adjacent` 为真的块（5 块，全在 `hard_多个技能条紧挨着.png`），
`delta_columns` **不许当成链的毛病读**。

**同一个根因还有一处**：条**右端被压暗**时旁证也停在压暗那一列（`r01_06_04` / `r01_05_04` /
`r01_07_02` 三块，逐条数字见 `判据读数.json` 的 `proof_caveat`）—— 也是**旁证错、链对**。

`判据读数.json` 里落了三条可判的线与逐块读数：

1. 旁证数到 **146 列**的块，链的比例应当是 1.0；
2. 不满的块，两条路不许差过 2 列；
3. 链读出来的列数不许比旁证多（多出来 = 跨过了本该停的地方）。

另外它逐块记了**黄菱形压在这一根上多少列**（模板 `assets/features/ready_diamond`，
整帧搜位置，搜索带与下限见 `scripts/bench_field_hard.py`）—— 用来判用户标的
「菱形挡住技能条」到底压在哪一根上。

## 覆盖文本的正文在这里

`判据读数.json` 的 `coverage` 是**唯一一处**写全了「这一批压到了哪些档、每一块怎么落」的
地方 —— 技力含义的「认不出」、空轨道单独可见、技力条掉到零这三档都在那一条里。
`scripts/bench_field.py` 的 `coverage` 与 `../场上干员/README.md` 的「没覆盖到什么」
**只引用它，不重抄**。

## 用法

```powershell
.venv\Scripts\python.exe scripts\bench_field_hard.py
```

同一批跑两次，两份 JSON 逐字节一样（没有时间戳、没有绝对路径、没有随机量）。
它**只建批与报读数**，不判断够不够 —— 那是规划者的事。
